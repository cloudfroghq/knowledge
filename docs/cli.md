# CLI reference

The `cloudfrog-knowledge` entry point (`knowledge.cli:main`) has nine subcommands; with none it is `serve`. `knowledge` is a second name for the same entry point: the usage (`--help`), `--version` (`knowledge X.Y.Z` or `cloudfrog-knowledge X.Y.Z`) and hints name the command you ran. Configuration errors print `<code>: <message>` on stderr, without a traceback, and exit with 2.

| Command | What it does | Exit codes |
|---|---|---|
| `serve [--transport stdio\|http] [--vaults FILE] [--profile all\|legacy]` | Starts the MCP server. The flags override `MCP_TRANSPORT`, `KNOWLEDGE_VAULTS` and `KNOWLEDGE_PROFILE`. | 2 on a configuration error (`E_PROFILE_UNKNOWN` with another profile) |
| `eval <args...>` | Runs `scripts/eval_retrieval.py` with those arguments (`--stdio\|--http`, `--queries`, `--vault`, `--provider`, `--rerank`, `--json`, `--markdown`, ...). Needs a source checkout. Guide: [`docs/eval/README.md`](eval/README.md). | the script's; 2 with `E_EVAL_UNAVAILABLE` if there is no `scripts/` |
| `vault-lint PATH [--format json] [--rules 1.2\|1.3] [--fix [--out DIR]]` | Checks a vault and prints JSON on stdout (`vault`, `files`, `rules`, `ok`, `errors`, `warnings`). | 0 without errors, 1 with errors, 2 with `E_LINT_PATH_NOT_DIR`, or with `--fix` `E_WRITE_FENCED` and `E_ARGUMENT_CONFLICT` |
| `doctor [--vaults FILE] [--brief] [--client] [--shape]` | Read-only diagnosis of whether this installation can serve; JSON, or one line of up to 200 bytes with `--brief`. `--shape` prints only aggregate size distributions of the default vault, for calibrating the benchmarks. | 0 healthy (also with a pending `init`), 1 with problems, 2 if the configuration does not load |
| `init [--vaults FILE] [--vault SLUG] [--root [SLUG:]NAME=DIR] [--search-dir DIR] [--max-depth N] [--repo [SLUG:]ID] [--all] [--drop [SLUG:]ID] [--yes] [--dry-run] [--json] [--force\|--refresh] [--exclude local\|gitignore]` | Client side: installs each vault's context packages into the checkouts selected on this machine. | 0; 1 on an unreadable vault or a conflict; 2 with `E_ROOT_UNKNOWN`, `E_CONTEXTS_REPO_UNKNOWN` or a configuration error |
| `migrate-index [--vaults FILE] [--vault SLUG] [--from-chroma DIR] [--build] [--prune-chroma]` | Prepares each vault's `index.sqlite` and copies the Chroma sidecars. | 0; 2 with `E_INDEX_VERSION_NEWER`, `E_INDEX_UNREADABLE` or `E_PRUNE_REFUSED` |
| `confluence export [--vaults FILE] [--vault SLUG] [--out DIR] [--space KEY] [--scope-prefix PREFIX] [--dry-run]` | Writes Confluence pages newer than the vault, outside every vault. | 0; 1 if the report has an error; 2 with `E_WRITE_FENCED`, `E_SECRET_MISSING` or an unknown vault |
| `memory-bridge sync [--vaults FILE] [--vault SLUG] [--card]` / `memory-bridge promote list\|stamp` | Publishes the vault to the local memory server; wraps `memory project <slug> promote`. | see below |
| `jira sync [--vaults FILE] [--vault SLUG] [--since ISO\|-Nd] [--dry-run] [--max-issues N] [--json] [--auto]` | Jira issues as tasks of the local memory server. | 0; 1 on `E_JIRA_*` or memory down midway; 2 if it could not be attempted; `--auto` always 0 |

## Command details

### `serve`

Starts the MCP server, over stdio (the default) or HTTP; `cloudfrog-knowledge` with no subcommand is `serve`. `--transport`, `--vaults` and `--profile` override `MCP_TRANSPORT`, `KNOWLEDGE_VAULTS` and `KNOWLEDGE_PROFILE`. It exits with 2 on a configuration error, for example `E_PROFILE_UNKNOWN` with a profile other than `all` or `legacy`. Serving over HTTP, with its bearer, is walked through in [Run over HTTP](getting-started.md#run-over-http).

### `eval`

Runs `scripts/eval_retrieval.py` with the arguments that follow it, so it needs a source checkout: without `scripts/` it exits with 2 and `E_EVAL_UNAVAILABLE`. How to build a query set and read the results: [`eval/README.md`](eval/README.md).


### `vault-lint`

Without `--fix` it writes nothing. `--rules 1.3` (the default) applies the vault rules: ISO `last_updated`, a known `type`, the vault's own `scope`, NFC paths without case collisions, runbooks that memory can index, and wikilinks that ignore code. `--rules 1.2` is the set that `reindex.validation` counts. Without `--rules` the result can differ from 1.2.0 (exit 1 where it was 0, for example from `E_FRONTMATTER_LAST_UPDATED`); `--rules 1.2` reproduces it. `--fix` (only with `1.3`) moves `updated`, `last_review` or `last_verified.date` to `last_updated`, only in the frontmatter, atomically and idempotently, and adds `fixed` and `remaining` to the JSON. It never writes in a served vault (`E_WRITE_FENCED`): run it on a checkout that is not served, or with `--out DIR` to fix a new copy outside every served vault, and deliver the change by PR. Error codes: `E_FRONTMATTER_UNPARSEABLE`, `E_FRONTMATTER_NOT_MAPPING`, `E_WIKILINK_UNRESOLVED` and, with `1.3`, `E_FRONTMATTER_LAST_UPDATED`, `E_SCOPE_FOREIGN`, `E_PATH_CASE_COLLISION`, `E_PATH_NOT_NFC`, `E_RUNBOOK_ID_INVALID`, `E_RUNBOOK_STATUS_INVALID`, `E_RUNBOOK_SERVICE_UNKNOWN`, `E_SERVICES_MAP_INVALID`. `E_ARGUMENT_CONFLICT` means `--out` is inside `PATH` or not empty. More in [`docs/install.md`](install.md), "Check a vault for its PR".

### `doctor`

Checks, without writing anything, whether this installation can serve: the discovery rule that won and the registry file; per vault, its directory, `vault.yaml`, embeddings provider, whether its key is defined (never the value) and whether there is an index; whether `KNOWLEDGE_HOME` is writable; the package and contract versions; the `rerank` block of each vault that declares a judge (names, never values); and the `tool_calls` block of the default vault (see [Call telemetry](operations.md#call-telemetry)). For each vault that declares `Contexts/config.json`, a `contexts` block says whether this machine has its `repos.local.json`; the ones that do not go in `init.pending` and, over stdio, in the `W_CONTEXTS_INIT_PENDING` warning. With `--brief`, one line of up to 200 bytes (the one the Claude Code plugin hook prints), which with a pending `init` is `knowledge doctor: init pending for vault(s) <slugs>; run: cloudfrog-knowledge init`. With `--client`, for a machine that consumes a remote server, it checks only the client side: that each vault exists and can be read, that its `Contexts/config.json` loads, its `repos.local.json`, and the state of each checkout according to an `init --dry-run` that neither scans nor prompts (`contexts.checkouts`); it skips the embeddings provider and key, the index, `vector_backend`, the judge, memory and bearers (`skipped`). A present checkout that is not in `apply` is `not-selected` (information); a selected one still to be installed counts as `init` pending; one with links to its package that is not in `apply` is the warning `W_CONTEXTS_LINKED_NOT_SELECTED`, and a `repos.local.json` without `apply` the warning `W_CONTEXTS_SELECTION_MISSING` (both exit 0; the healthy brief line adds `, <n> checkout(s) linked and not selected` or `, selection missing in <n> vault(s)`). A checkout that is a git repository without an `origin` remote is the warning `W_CONTEXTS_CHECKOUT_UNVERIFIED` (it does not fail: nothing proves it is another repository); a conflict is `E_CONTEXTS_CONFLICT`, and a checkout whose `origin` is another repository or that is not a git repository is `E_CONTEXTS_CHECKOUT_INVALID`. The healthy `--client` brief line is `knowledge doctor: ok, client, <n> vault(s), default <slug>`, plus `, <n> checkout(s) unverified` when there are such warnings. Exit 1 codes: `E_VAULT_PATH_MISSING`, `E_VAULT_PATH_NOT_DIR`, `E_VAULT_MANIFEST_MISSING`, `E_EMBEDDINGS_PROVIDER_UNKNOWN`, `E_EMBEDDINGS_KEY_MISSING`, `E_KNOWLEDGE_HOME_NOT_WRITABLE`; with `--client`, `E_VAULT_PATH_*`, `E_VAULT_MANIFEST_MISSING`, `E_CONTEXTS_INVALID`, `E_CONTEXTS_CONFLICT` or `E_CONTEXTS_CHECKOUT_INVALID`.

### `init`

For each registered vault that declares `Contexts/config.json`, it locates each root (flag, environment, `repos.local.json`, the vault's `default`, git checkouts whose `origin` matches under `--search-dir` (by default `~/Projects` and the parents of known paths), or a prompt, except with `--yes`). It decides which checkouts receive a package on this machine: the `apply` list of `repos.local.json` ([ADR-049](adr/ADR-049.md)). `--repo ID` adds, `--all` adds every present checkout with a package, and `--drop ID` removes the id and deletes only that checkout's links to `Contexts/<package>/`. A file without `apply` adopts the checkouts that already have their package installed; a machine with nothing to adopt and no flags asks in a terminal and, with `--yes` or without a terminal, installs nothing and lists the present checkouts with the `--repo ID` hint; an id the registry no longer declares leaves with a warning. It writes `<config home>/knowledge/<slug>/repos.local.json` (honoring `$XDG_CONFIG_HOME`) and installs the `Contexts/<context>/` package of each selected, present checkout (present but unselected ones stay `not-selected`): relative links (`link`, the only recommended mode) or a copy (`copy`, kept for compatibility), plus ignore entries in `.git/info/exclude`. It skips checkouts that are not there. A `.claude` that is a real directory in the checkout stays real and receives one link per entry of the package's `.claude` (and per entry of a versioned `.claude/<collection>/`); what the checkout versions in git is its own and is kept with a warning, without conflict ([ADR-048](adr/ADR-048.md)). It never replaces unversioned content of its own without `--force` (which sets it aside as `<name>.pre-ai-context.bak-<epoch>`), resyncs a copy with `--refresh`, never writes inside a vault (`E_WRITE_FENCED`) and is idempotent. It ends by saying where each file lives; `--dry-run` also shows selection changes. Exit 1 also covers `E_CONTEXTS_INVALID` (including an `apply` that is not a list of ids), a `--root` that is not a directory, and an `origin` that is not the declared remote; `E_CONTEXTS_REPO_UNKNOWN` is a `--repo` or `--drop` that no vault declares. See [`docs/install.md`](install.md), "Initialize the client", and [ADR-047](adr/ADR-047.md).

### `migrate-index`

Prepares each vault's `index.sqlite` without embedding anything, and copies `usage_stats.json` and the learned weights of `link_graph.json` from a Chroma directory (it never opens the Chroma database; `chromadb` is not a dependency). It prints one JSON line per vault (`{vault, outcome, index_version, from}`, with `outcome` `created`, `migrated`, `up_to_date` or `upgraded`). A second run writes nothing. `--build` indexes right away; `--prune-chroma` deletes only `chroma.sqlite3` and Chroma's segment directories. The image runs it before `serve`.

### `confluence export`

Writes under `--out` (by default `<data_dir>/<slug>/confluence-export/`) the Confluence pages newer than their vault file, with the vault's frontmatter and the `last_updated` of the day the page changed. It never writes in a vault: an `--out` inside any served vault, or a file that resolves there through a symlink, is `E_WRITE_FENCED` and no file is written. JSON on stdout (`{out_dir, written, unchanged, errors, ...}`). Exit 1 means nothing was tracked in the scope or a page could not be read. Promotion to the vault is a human PR ([`docs/runbooks/promote-confluence.md`](runbooks/promote-confluence.md)).

### `memory-bridge sync`

Publishes the vault to its project (`memory.project`) in the local memory server: with `--card`, it creates or updates the card (`display_name` from `name`, `jira_project` from the first `integrations.jira.projects`, `knowledge_hub_path` from `memory.hub`; what the vault does not declare is not sent), then has memory rescan `Runbooks/` (`source: vault-fs`). It writes only to memory, on loopback, and requires the `memory-bridge` feature. JSON on stdout (`{vault, memory_project, ok, card, runbooks}`). Exit 1 if memory rejected a step (`E_MEMORY_WRITE_FAILED` with `http_status` and `reason`); 2 with `E_FEATURE_DISABLED`, `E_MEMORY_PROJECT_MISSING`, `E_MEMORY_TOKEN_MISSING` or `E_MEMORY_URL_NOT_LOOPBACK`.

### `memory-bridge promote`

Usage: `memory-bridge promote list [--types LIST] [--limit N]` and `memory-bridge promote stamp OBS --knowledge-ref PATH`. They wrap `memory project <slug> promote list|stamp --json` (`MEMORY_BIN` or `memory` on the `PATH`): the pinned observations that can become a document, and the record, on the observation, of the document the PR merged. Nothing is written in the vault; `stamp` requires `--knowledge-ref` to be an existing `.md` in it. Prints memory's JSON. Exit 1 if memory answers an error (its JSON envelope); 2 with `E_KNOWLEDGE_REF_INVALID`, `E_ARGUMENT_OUT_OF_RANGE` (a `--types` value that is not a lowercase observation type), `E_MEMORY_UNAVAILABLE` (missing binary, more than 30 s, or output without JSON) or a configuration error.

### `jira sync`

Copies the issues of the vault's `integrations.jira` projects updated since `--since` (by default the cursor minus one day after a complete run, the exact cursor after a truncated one, or 30 days; tasks that memory rejected are read again by key on the next run) as tasks of its memory project, one per issue and per `jira_key`. Unlike the tool, it writes unless `--dry-run`. One summary line, or the full report with `--json`. `--auto` runs every vault that declares `jira`, has its variables and has met `sync.throttle_minutes`; it is what the session hook launches. Over stdio only, since it writes to the local memory. Exit 1 with `E_JIRA_UNAVAILABLE`, `E_JIRA_AUTH_FAILED`, `E_JIRA_SYNC_STALLED` or memory down midway (the report has `error`); 2 with `E_FEATURE_DISABLED`, `E_SECRET_MISSING`, `E_MANIFEST_INVALID`, `E_MEMORY_TOKEN_MISSING` or another configuration error. See [`docs/runbooks/sync-jira.md`](runbooks/sync-jira.md).

## Command label in hints

The hints that say what to run (the `doctor --brief` line, `init.command` in the `doctor` JSON, the `W_CONTEXTS_INIT_PENDING` warning, the `_README` of each `repos.local.json`, the hint of an `init` conflict and the header of its report) name `cloudfrog-knowledge init` or `cloudfrog-knowledge doctor`, or `knowledge init` and `knowledge doctor` when you ran the CLI as `knowledge`. A vault whose clients call `init` and `doctor` through their own scripts sets `KNOWLEDGE_COMMAND_LABEL` in them, and the hints name those scripts instead of this CLI, under either name:

| `KNOWLEDGE_COMMAND_LABEL` | Hint for `init` | Hint for `doctor --client` |
|---|---|---|
| unset or blank | `cloudfrog-knowledge init` (`knowledge init` if you ran `knowledge`) | `cloudfrog-knowledge doctor --client` (`knowledge doctor --client`) |
| `Contexts/scripts/{command}.sh` | `Contexts/scripts/init.sh` | `Contexts/scripts/doctor.sh` |
| `acme-knowledge` | `acme-knowledge init` | `acme-knowledge doctor` |

It is one variable for both commands: `{command}` is replaced by the subcommand and, without it, the subcommand goes after the label. With a label defined, the hint adds no flags: a script carries its own. No other environment value appears in a hint.
