# Tool contract changelog

Each contract version has its golden directory at `tests/golden/v<version>/`. A directory with a `SHA256SUMS` file is frozen: no test or command re-records it, and `tests/test_contract_frozen.py` fails if a single byte changes, on any Python, whether or not `sqlite-vec` loads. What each frozen version still guarantees is checked by `tests/golden_compat.py` on the parsed JSON, in a session of its own: every frozen key comes back with the same value. There are three exceptions. When the frozen version is earlier than 1.2.0 and the served one is 1.2.0 or later, `search`, `search_deep` and `context_pack` (the tools that rank by the index) are compared by shape — same keys and types per row, `isError`, no more rows than `limit`, at least one row where the frozen version had any, `used_tokens ≤ budget_tokens` — and not by `score`, order or membership, and `reindex.export_hint` only has to still be present. Against any frozen version other than the served one, `list_vaults.contract` and the first line of `instructions` must name the served version. `test_the_store_bound_set_is_exactly_the_ranked_tools` fails if any of those sets grows. The version the package serves lives in `src/knowledge/contract.py` (`CONTRACT_VERSION`), and `TOOL_SINCE` says in which version each tool appeared. Since 2.0.0, which deliberately breaks the 1.x series, only the 1.4.0 goldens are replayed against the server, and each one first goes through the declared migration in `tests/golden_compat.py` (`migrate_1_4_to_2_0`): the `R<n>` rules of the "Breaking" table of `## 2.0.0` and no others.

## 2.0.0

Released on 2026-10-13 with `cloudfrog-knowledge` 0.6.0 (tag `v0.6.0`).

The goldens live in `tests/golden/v2.0.0/`, frozen with their `SHA256SUMS` (the six sessions described below), recorded over stdio against `tests/fixtures/vault/` with the usual launcher, a real `SQLiteStore` and `KNOWLEDGE_REQUIRE_SQLITE_VEC=1`, with the Python 3.12 of the `uv` environment. Sessions: the main one (profile `all`, default output, text only, 10 tools), `structured` (`KNOWLEDGE_STRUCTURED_OUTPUT=1`, of which only the catalog is recorded, `tools_list__structured`), `features` (a copy of the fixture whose `vault.yaml` declares `features: [flows, governance, confluence]`, same `slug` and no `review` block: `tools_list__features` with 15 tools and the cases of those tools), `legacy` (`KNOWLEDGE_PROFILE=legacy`: `tools_list__legacy` with the 16 tools of 1.4.0 in their order, `search_code` and `get_flow__legacy`), the one that declares `jira`, and the one with the `kev` judge on loopback. The goldens environment sets `KNOWLEDGE_STRUCTURED_OUTPUT`, `KNOWLEDGE_TEXT_INDENT` and `KNOWLEDGE_PROFILE` to empty, so that a local `.env` does not change what is recorded; the `legacy` session sets its own. The 1.4.0 replay runs the `V1_4_0_CASES` cases in full and in order, in a single session over the copy from the `features` session, so that each `search` finds the usage counters it was recorded with.

### Rule

Breaking and declared. Every change of shape, default, name or code is a row of "Breaking", with its id `R<n>`, and a rule of `MIGRATIONS_2_0` in `tests/golden_compat.py` with the same id; `test_every_2_0_migration_is_declared_in_the_changelog` requires the two sets to match. Whatever is not in that table comes back with the same value as in 1.4.0: the 1.4.0 goldens, migrated by those rules and only those, are compared key by key with what 2.0.0 answers. The text blocks (`content`) are the canonical answer of every tool; `structuredContent` and `outputSchema` are a view of the same JSON that the operator turns on with `KNOWLEDGE_STRUCTURED_OUTPUT=1`, with no version change. No 2.x client may depend on that view. Every tool error is `isError: true` with a text block containing `E_<CODE>: <message>`; the SDK prefixes it with `Error executing tool <tool>: `, except in two cases the server answers without reaching the tool, which start directly with the code: `E_TOOL_RETIRED` and `E_FEATURE_DISABLED` for a tool this process does not register (`E_FEATURE_DISABLED` on a vault that does not declare the extension, with the tool registered, does carry the prefix). Whoever reads the code looks for it with `E_[A-Z_]+: `, not at the start of the text. The tool descriptions in `tools/list` are not a value the 1.4.0 replay compares: those of `get_document`, `search`, `search_by_metadata`, `search_deep`, `get_related`, `get_impact`, `reindex` and `sync_confluence` change in 2.0.0, to name the new defaults and caps, without a row of their own.

### Added

- Public tool profiles: `all` (the usual one) and `legacy`, chosen with `serve --profile {all,legacy}` or `KNOWLEDGE_PROFILE` (the flag wins; empty counts as absent). Any other value stops startup with `E_PROFILE_UNKNOWN` and exit code 2, without echoing the received value. `legacy` registers the 1.4.0 catalog, name by name and in its order (`tests/golden/v1.4.0/tools_list.json`): the `flows`, `governance` and `confluence` tools without looking at `features`, and `search_code` in its position, with the 2.0 schemas and responses; `sync_jira` stays conditional on `jira`. It lives for one release.
- `GET /health` gains `profile`, the profile the process serves.
- Tool code `E_TOOL_RETIRED`: the call to a tool the contract removed, with the redirection to what replaces it. `E_FEATURE_DISABLED` now also covers tools: that of an extension no served vault declares, and that of an extension called on a vault that does not declare it; the message names the vaults that do declare it.
- Extension registry: `flows`, `governance` and `confluence` become conditional, like `jira`. The server still imports `knowledge.review` at startup for every vault: `needs_review` and `age_days` do not depend on `governance`.
- `cloudfrog-knowledge doctor`: the `tool_calls` block counts `search_code` under `deprecated` and not under `unregistered`.
- `get_document` gains the `full_metadata` parameter (`full_metadata=True` returns the whole frontmatter) and reading by `chunk_id` without `file_path` (R4).
- Tool codes `E_ARGUMENT_MISSING` (a call that does not name what to act on), `E_ARGUMENT_RETIRED` (a removed parameter that the schema keeps in order to warn, R20), `E_FILE_NOT_FOUND` and `E_SECTION_NOT_FOUND` (R5).
- `scripts/measure_tokens.py --flow defaults`: `search(query)` and `get_document(chunk_id=...)` with no other parameters, the `instructions` protocol (R17).
- Tool codes `E_FILE_NOT_IN_GRAPH` (R10), `E_FLOW_NOT_FOUND` (R13) and `E_SCOPE_EMPTY` (R12); `E_SECRET_MISSING` now also covers the call to `sync_confluence` without credentials. `direction: both` in `get_related`; `total` and `offset` in `search_by_metadata`.
- New goldens of the main session: `search__excerpt`, `search__limit_out_of_range`, `get_document__by_chunk`, `get_document__full_metadata`, `get_document__missing`, `get_document__section_missing`, `get_document__no_target`, `get_document__include_metadata`, `search_by_metadata__all`, `get_related__suggested`, `find_path__missing` and `reindex__pull`; of the `features` session, `get_flow__missing` and `compare_flows__missing`.
- New goldens: `tools_list__structured`, `tools_list__features`, `tools_list__legacy`, `search_code__retired` and `get_flow__feature_disabled` (main session), `get_flow__legacy` (`legacy` session).

### Removed

- `search_code` from the `all` profile (R15); the `legacy` profile serves it for one more release.
- `export_hint` of `reindex` and the tool's implicit `git pull` (R11).
- `space_key` and `page_id` of `sync_confluence` (R12).
- Every successful response with an `{"error": …}` object: `get_document` (R5), `find_path` (R10), `sync_confluence` (R12), `get_flow` and `compare_flows` (R13). A tool error is always `isError` with a stable `E_` code. Two error objects remain that are part of a report and not the whole response: the `errors[].error` rows of `sync_confluence` (a file that could not be compared) and the coded `error` of `sync_jira` when memory fails midway through a run, which accompanies the counts of what was in fact written.
- Reading a file outside the vault with `get_document`: a path with `..`, an absolute one or a symlink that leaves the vault answers `E_FILE_NOT_FOUND`, with the same message as a nonexistent file, so as not to reveal whether it exists. In 1.4.0 `get_document(file_path="../../../README.md")` read the file, also with a read-only bearer over HTTP. No golden changes.
- The compatibility replays of the 1.0.0, 1.1.0, 1.2.0 and 1.3.0 goldens against the live server (`test_every_1_0_0_golden_is_still_honoured` and the next three, with their sessions). Their directories remain frozen with `SHA256SUMS` and `tests/test_contract_frozen.py` verifies them byte by byte; what they guaranteed reaches 2.0.0 through 1.4.0, which honored all of them and is frozen. The replay that remains is that of 1.4.0, migrated by the "Breaking" rules.

### Deferred

- The 1.2.0 deferral "`KNOWLEDGE_STRUCTURED_OUTPUT=0` by default, 2.0 at the latest" is closed by R19: the owner ran the Claude Desktop session with a local stdio server at `0` and with the remote deployment at `1`, and `docs/adr/ADR-046.md` supersedes decision 13 of `docs/adr/ADR-043.md` on this point.
- Claude Desktop through `mcp-remote` with `KNOWLEDGE_STRUCTURED_OUTPUT=0`: the ADR-042 condition named that path, which is the one used by AcmeDrive's clients, and the owner's session did not cover it. It is verified with the ADR-042 procedure (a `search` and a `get_document` against a local 2.0.0 over HTTP on loopback) as a condition for moving the AcmeDrive deployment to 2.0.0; if it fails, that deployment sets `KNOWLEDGE_STRUCTURED_OUTPUT=1`.
- `snippet` in the default row. With `text-embedding-3-large` on the fixed corpus, the 120-character excerpts of the five rows cover the answer in 1 of 50 queries and cost 191 tokens per search; with 400, 14 of 50 for 571. For choosing which row to read, none beats reading the first (36 of 50). It is reopened if a measurement shows at least 30 % of reads avoided at no more than +100 tokens.
- `discovered_via` of `search_deep` as `doc_id`: about 10 tokens per hop row, but `doc_id` does not travel in the default row and the agent could not resolve the reference.
- The Confluence importer into a derived index (`imported`, `admin` scope): `sync_confluence` remains read-only (ADR-044) and promotion is a human PR.

### Added

- `vault.yaml`: `rerank` key, the judge that reorders the results of `search` and the variable its key comes from, never the key itself. Keys: `provider` (`none` by default, `jev` or `kev`), `default` (`off` by default or `on`), `model` (a pinned version: `jev-latest` is rejected because the alias changes without notice; `kev` accepts `kev-latest`), `key_env`, `candidates` (1 to 12, 10 by default), `units_per_doc` (1 to 3, 2), `timeout_ms` (200 to 10,000, 1,500; up to 60,000 with `kev`), `max_input_tokens` (1,000 to 30,000, 20,000), `max_usd_per_day` (1.00; 0 for no cap), `conditional_gap` (`null`), `never_send` (vault path prefixes whose content never leaves the machine) and `base_url` (`kev` only, loopback only). Without the block, or with `provider: none`, the vault has no judge and behaves as in 1.3.0.
- `rerank.key_env` names a variable of the vault itself: `TYPESAFE_API_KEY` (`jev`) or `KEV_API_KEY` (`kev`) only in the default vault, and `<PREFIX>_TYPESAFE_API_KEY` or `<PREFIX>_KEV_API_KEY` in any, with the slug in uppercase and underscores as the prefix. With `jev` the URL is TypeSafe's and the vault does not change it: a `base_url` with `jev`, or with `kev` outside `127.0.0.1`, `localhost` or `[::1]`, is `E_MANIFEST_INVALID`.
- Operator configuration, which a vault does not define: `KNOWLEDGE_RERANK` (`off` turns off every judge in the process; a value other than `off` also turns it off and warns), `KNOWLEDGE_RERANK_PROVIDERS` (list of allowed providers, `jev,kev` by default), `KNOWLEDGE_RERANK_BASE_URL` (`https://api.typesafe.ai` or an `http` URL on loopback) and `KNOWLEDGE_RERANK_TIMEOUT_MS` (200 to 60,000). A value that is not valid is ignored with a warning.
- Configuration codes: `W_RERANK_INVALID` (a malformed `rerank` block, or a `KNOWLEDGE_RERANK*` variable that is not valid: only that vault is left without a judge and the server starts) and `W_RERANK_KEY_MISSING` (a vault declares a provider and the variable of its key is empty: it starts anyway, over stdio and over HTTP, with `default: on` or without it, and searches without a judge). Tool code: `E_RERANK_NOT_CONFIGURED`.
- `Judge` port (`src/knowledge/ports.py`) with `JudgeUnit`, `JudgeVerdict`, `JudgeUnavailable` and `NullJudge`, and `VaultRuntime.judge` in the registry: a `NullJudge` unless the server injects another with `judge_factory`. It changes no response.
- System One judge (`src/knowledge/judges.py`, ext layer, registered as the `rerank` extension of `src/knowledge/extensions.py`, which a vault activates with its `rerank` block and not with `features`): a single adapter for `jev` (`https://api.typesafe.ai/v1/systemone`) and `kev` (`http` on loopback only), with the standard library and no new dependencies. One request per query with a `noul` question per passage, one persistent connection per thread, a total deadline that covers DNS resolution, connection, TLS and read, a response body of up to 256 KB, no proxy and no redirects. Every failure is `JudgeUnavailable` with `auth` (401, 403), `unavailable` (429, 529 and any other status, connection refused or cut), `timeout` or `invalid_response`, without the URL, the body or the key. The server imports it only for a vault that declares a provider the operator allows.
- `search(..., rerank=None)`: new parameter, at the end of the signature, `string` or `null`. `"on"` reorders the hybrid results with the vault's judge, `"off"` never does and omitted follows the vault's `rerank.default`. Any other value is `isError` with `E_ARGUMENT_OUT_OF_RANGE`; `"on"` on a vault without `rerank.provider` is `isError` with `E_RERANK_NOT_CONFIGURED`. Both checks run without searching or counting anything: no usage counter or link weight moves. The caller does not choose the provider: the vault declares it (curated content, human PR) and the operator allows it; a parameter never enables a provider the vault does not declare.
- How it reorders (`src/knowledge/rerank.py`, core layer, no network): a hybrid *pool* of `max(limit, 20)` documents (twice the chunks per path), without recording usage; the judge reads the first `rerank.candidates`, each with up to `rerank.units_per_doc` pointer blocks (the text returned by `get_document(chunk_id=…)`, cut at 2,000 characters: first the heading block of the best dense chunk and then those that weigh most for the query), all in a single request. Fused score: `round(hybrid · boost · (0.8 + 0.5 · p), 2)`, with `p` the best probability among the document's blocks; a document the judge did not see keeps its `score`. It is ordered by `(-score, file_path)` and cut at `limit`; only the final rows count as usage and as co-retrieval. Only `mode="hybrid"` without `include_memories` is reordered: the content of memories never leaves the machine.
- Reordered rows: `rerank_score` (the probability of the chosen block, 2 decimals) in every row the judge read, and `chunk_id`, `section` and `snippet`, when requested, name that block. `fields` accepts `rerank_score`, at the end of the canonical order; requested without rerank applied, the key does not appear. `score` remains ordinal: it can exceed 1.
- `_meta["knowledge/rerank"]` of the `search` result, only when the call evaluated rerank (`rerank` present or `rerank.default: on`): `{provider, model, applied, reason, candidates, units, cache_hits}`, deterministic and without latencies. `reason` is `null` when it was applied or one of `off`, `timeout`, `unavailable`, `auth`, `invalid_response`, `breaker_open`, `budget_tokens`, `budget_day`, `memories_included`, `gap`, `no_candidates`, `disabled`, `key_missing` and `mode`. A failing judge is never `isError`: the response is that of the search without rerank, with its `reason`.
- Judge limits, per vault: `timeout_ms` deadline (or `KNOWLEDGE_RERANK_TIMEOUT_MS`), estimated tokens per request `ceil(characters / 2.95) + 50 · units + 300` over the compact JSON of `state` without ASCII escapes and trimmed to `max_input_tokens` (extra blocks first, from the bottom up; then whole documents), the day's spend in USD against `max_usd_per_day`, shared by all the vault's processes because it lives in its `usage_stats.json`, a cache of judged blocks (4,096 entries, 7 days, per query, `chunk_id` and text hash: a repeated query only sends the blocks that are missing) and a circuit breaker (3 consecutive failures open it for 60 s; a rejected key, 15 min).
- `usage_stats.json`, `rerank` section: calls, applied, skipped by `reason`, blocks, cache hits, billed tokens, USD, judge latency histogram in fixed buckets, the day's spend and searches per day (with and without rerank). Never a query or a passage.
- `cloudfrog-knowledge doctor`: `rerank` block for each vault that declares a provider, with `provider`, `default`, `model`, `key` (`ok` or `missing:<VARIABLE>`, never the value), whether the operator allows it, the effective configuration and the aggregates of its `usage_stats.json` (`calls`, `applied_rate`, `cache_hit_rate`, `p50_ms`, `p95_ms`, `usd_total`, `usd_today`, searches of the day). `doctor --brief` adds `rerank <slug>:<provider>/<on|off>` when some vault declares it.
- New goldens: `search__rerank_unconfigured` in the main session and a third session with a `kev` judge on loopback (`tests/systemone_fakes.py`, deterministic, the mode is chosen with a marker in the query): `search__rerank_off`, `search__rerank`, `search__rerank_fields` (the same query, served from the cache) and `search__rerank_down` (the judge answers 529). The goldens launcher sets the keys and variables of every judge to empty and rejects any connection outside loopback.

Choosing the provider stays with the vault and the operator, not the caller, because it decides where the content travels; the 1.x series inherits `on|off`. ## 1.2.0

Released on 2026-10-12 with `cloudfrog-knowledge` 0.3.0 (tag `v0.3.0`).

Rule of this version (`docs/adr/ADR-043.md`, which extends ADR-042): additive in keys, parameters and defaults; the values that come out of the ranking (`score`, order and row membership) cease to be stable across indexes and are declared in "Changed (non-additive)". `score` remains ordinal: it is not compared across indexes or used as a threshold. No tool disappears, no parameter changes name, type, default or `required`, and `tools/list` is byte-for-byte identical to that of 1.1.0.

Each vault is served from a single SQLite file (`index.sqlite`): one row per document, its chunks, an FTS5 index (`unicode61 remove_diacritics 2`) and its float32 vectors, which `sqlite-vec` 0.1.9 queries by exact KNN with `k = ?`. Where the extension does not load, the same vectors are sorted by brute force with the standard library (`vector_backend: python`): the same result except for exact similarity ties at the boundary of `k` (`vec0` chooses among the tied ones in its own order; the fallback breaks ties by `file_path` and chunk number), about 110 ms per query with 1,480 vectors of 3,072 dimensions against about 10 ms with `sqlite-vec` (median of 20 queries on an Apple M2 Max, Python 3.12.12, SQLite 3.50.4). The lexical part of the hybrid search is FTS5 BM25 per chunk (weights 3/2/1 over title, section and text; each term of 4 characters or more searches as a prefix), with the same fusion `0.7·semantic + 0.3·lexical` as 1.1.0. Goldens in `tests/golden/v1.2.0/`, recorded over stdio against `tests/fixtures/vault/` with the usual launcher, a real `SQLiteStore` and `KNOWLEDGE_REQUIRE_SQLITE_VEC=1` (the server does not start if the extension does not load), with the Python 3.12 of the `uv` environment.

Measurement over `vault/cloudfrog`, 50 queries (`docs/eval/baseline.md`, `docs/eval/tokens.md`): with `text-embedding-3-large`, recall@5 **0.930** (gate ≥ 0.890; per-document TF-IDF over the same index gives 0.920, so the lexical side is FTS5) and MRR@5 0.897; the `instructions` protocol flow costs 794 tokens on average (gate ≤ 853, target ≤ 800) with `answer_terms` coverage 0.540 (gate ≥ 0.540). With the `none` provider, recall@5 0.837 (floor 0.803).

Side effects with no change of shape:

- A vault's index lives in its index directory: `index.sqlite` next to `link_graph.json`, `usage_stats.json`, `index_meta.json` and `skipped_files.json`. In a `VAULT_PATH` deployment the directory is the first of `KNOWLEDGE_INDEX_DIR`, `CHROMA_PERSIST_DIR`, `<KNOWLEDGE_HOME>/<slug>` (only with an explicit `KNOWLEDGE_HOME`) and `<root>/.data/<slug>`; in a `vaults.yaml`, `<data_dir>/<slug>`. With `CHROMA_PERSIST_DIR` the index lands on the same volume as Chroma's, with its sidecars.
- An index built with a different provider, model or chunk plan is emptied and fully re-embedded when the first tool is served (`E_INDEX_PROVIDER_MISMATCH` in the log); with `openai`, that costs one full reindex, once.
- A process's first indexing loads the learned weights from `link_graph.json` and then rebuilds the edges, so a file that carries only weights keeps them.
- A document whose embedding fails is not written (neither its row nor its chunks), so the selector's idf `N` counts only indexed documents, as in 1.1.0.
- Two processes indexing the same directory take turns (`flock` on `.index.lock`).
- `link_graph.json` stores `"resolver"`: when opening an index whose graph carries a different version (or none), the indexer registers the links again from the vault, keeps the weights and saves the graph without embedding anything.
- `index_meta.json` adds `chunker` and `index_version`.
- The image sets `KNOWLEDGE_HOME=/data/index` and its entrypoint runs `migrate-index` (without embedding) and then `serve`, with the migration report on stderr. The Compose files in `infra/` set `KNOWLEDGE_INDEX_DIR=/data/index/<slug>` on a volume of their own and leave the Chroma one mounted only as the source for `migrate-index`.

Released on 2026-10-12 with `cloudfrog-knowledge` 0.2.0 (tag `v0.2.0`).

Pointers, on demand only (with `fields` or `snippet`):

- `doc_id`: the first 10 hex characters of `sha1(file_path)`; stable across processes and index rebuilds, scoped to a vault. The server resolves it with a `doc_id → file_path` map built from the vault's files, which is discarded on every indexing (the webhook's too) and rebuilt once on an unknown `doc_id` before answering `E_DOC_ID_UNKNOWN`.
- `chunk_id`: `<doc_id>:<n>`, with `n` the 1-based ordinal of the heading in document order and `0` the preamble; headings inside fenced code blocks do not count. The block runs from the heading to the next one of equal or lower level.
- `section`: heading text of that `chunk_id`, suitable for the `section` of `get_document`; the `chunk_id` disambiguates repeated headings.
- Section selector: lexical and deterministic, over the body read from disk. The candidates are the blocks a `chunk_id` can name (the preamble and each heading's block). Each block is scored over its first 2,000 characters, those read by the `get_document(..., max_chars=2000)` of the `instructions` protocol (`pointers.READ_WINDOW_CHARS`): each query term with positive idf (that of the keyword index) that appears in that window adds `idf · (1 + ln(occurrences))`. The highest wins; on a tie, the block with more text inside the window and, after that, the first. With no term of positive idf in any window, `chunk_id` and `section` are `null`. It only reads files: it moves no usage counters or graph weights. On `tests/fixtures/vault/` it picks the same sections as the by-ranges rule it replaces, so no golden changes because of the selector; on the real vault it raises the protocol's `answer_terms` coverage from 0.380 to 0.560 (`docs/eval/tokens.md`).

New error codes (text `<code>: <message>` after FastMCP's `Error executing tool <tool>: ` prefix, no traceback): `E_FIELD_UNKNOWN`, `E_ARGUMENT_CONFLICT`, `E_ARGUMENT_OUT_OF_RANGE`, `E_CHUNK_ID_INVALID`, `E_DOC_ID_UNKNOWN`, `E_DOC_ID_AMBIGUOUS`; `E_VAULT_UNKNOWN` already existed as a configuration error and is now also returned by a tool.

New goldens in `tests/golden/v1.1.0/`, recorded after the 1.0.0 read cases and before `sync_confluence` and `reindex`: `search__pointers`, `search__snippet`, `search_deep__pointers`, `get_document__chunk` (the `chunk_id` returned by `search__pointers`), `get_document__sections`, `get_document__argument_conflict`, `search__unknown_vault`, `search_by_metadata__page` (`limit=2, offset=1`), `search_by_metadata__facets` (tag `service/middleware`; the counts are verified by hand against the fixture's frontmatter in `tests/test_listing_tools.py`), `get_related__fields`, `get_impact__counts` (`max_items=1, counts=True`) and `get_stale_docs__missing`. ### New tools

They are registered after those of 1.0.0, in this order, and belong to the internal `core` profile.

| Tool | Parameters (default) | Response |
|---|---|---|
| `list_vaults` | none; it is the only tool without `vault`, because it is the one that enumerates them | `{contract, default, vaults}`: `contract` is the contract version (`1.1.0`), `default` the slug that serves a call without `vault`, and each row of `vaults` is `{slug, name, default, features}` in the order they were registered, with `features` sorted. It never returns a vault's path, repository or environment variables, and opens no index: it only reads configuration |
| `context_pack` | `query`; `budget_tokens` (`3000`); `include_memories` (`false`); `vault` (`null`) | `{query, vault, budget_tokens, used_tokens, items, dropped, sources_used}` and, only if memory was requested and could not be read, `degraded: [{source: "memory", code}]`. See below |

`context_pack` assembles a task's context in one call, with a hard token cap:

1. It searches the query in the vault like `search` in `hybrid` mode with `limit=8`; `include_memories` passes through as is, so with `true` the documents of the vault's memories folder also come in.
2. For each row it takes the block of the section the query hits (the same selector as `search` pointers). If the file contains no term of the query, it takes the document's opening: the preamble or, without a preamble, the first heading's block. A vault item is `{source: "vault", doc_id, file_path, chunk_id, section, score, text}`; its `text` is exactly the `content` of `get_document(file_path, chunk_id=…)` without trimming.
3. With `include_memories=true` it also requests up to 5 observations from the memory server (`GET /search` of the vault's memory project) and fuses the two lists by reciprocal rank (k = 60; at equal rank, vault first). A memory item is `{source: "memory", id, type, title, text}`.
4. It fills in that order. An item whose `chunk_id` already got in, or whose text is contained in that of an already delivered item, goes to `dropped` with `reason: "duplicate"`. One that fits goes in whole; one that does not fit is trimmed to the remaining space, with `truncated: true`, if at least 200 tokens remain, and otherwise goes to `dropped` with `reason: "budget"`. Memory items never take more than 30 % of the budget. A `dropped` entry names the item without its text: `{source: "vault", doc_id, file_path, chunk_id, reason}` or `{source: "memory", id, reason}`.
5. Tokens are estimated without a tokenizer: `ceil(UTF-8 bytes / 4)` of each item's compact JSON, keys included. `used_tokens` is the sum of the delivered items and never exceeds `budget_tokens`. On Spanish text it overestimates (accented letters take two bytes).

`sources_used` lists, in the order `vault, memory`, the sources with at least one delivered item. `budget_tokens` outside [500, 12000] is `E_ARGUMENT_OUT_OF_RANGE`. Asking for memory never makes the tool fail: if it cannot be read, the pack is assembled from the vault alone and `degraded` says why, with one of these new codes:

| Code | When | Was there a connection? |
|---|---|---|
| `E_MEMORY_TOKEN_MISSING` | `MEMORY_HTTP_TOKEN` is not defined | No |
| `E_MEMORY_URL_NOT_LOOPBACK` | `KNOWLEDGE_MEMORY_URL` is not `http` over `127.0.0.1`, `localhost` or `::1`; a warning is also logged when the vault opens | No |
| `E_MEMORY_PROJECT_MISSING` | the vault declares no memory project (`memory.project` in `vaults.yaml` or in its `vault.yaml`) | No |
| `E_MEMORY_UNAVAILABLE` | connection refused, more than 1 s without a response, a status other than 200 (a 401 included) or a body that is not a JSON list | Yes |

The memory client (`src/knowledge/memory_http.py`, standard library only) only reads and sends on every request `Authorization: Bearer <MEMORY_HTTP_TOKEN>`, `X-Memory-Client: cloudfrog-knowledge/1.1.0` and `Accept: application/json`; without a token it does not call. It connects directly to the URL's host: it ignores `http_proxy`, `HTTP_PROXY` and the other proxy variables, so the bearer never goes through a proxy. `KNOWLEDGE_MEMORY_URL` defaults to `http://127.0.0.1:6366`. A `null` response from the memory server counts as zero hits. Neither the token nor the request URL (which carries the query) appears in a message or in the log.

New goldens, recorded at the end of the read cases and before `sync_confluence` and `reindex`: `list_vaults`, `context_pack` (`budget_tokens=600` over the fixture: it delivers seven sections and leaves one in `dropped` because of budget) and `context_pack__memory_unconfigured` (the same call with `include_memories=true`; the golden server sets `MEMORY_HTTP_TOKEN` to empty, so it answers `degraded` with `E_MEMORY_TOKEN_MISSING` and no golden reads a memory server). No previously recorded response changes value.

Baseline notes:

- The order of `find_path`, `get_related` and `get_impact` depends on `PYTHONHASHSEED` and is not contract in 1.0.0 (ADR-040). Score ties in `search` and `search_deep` do not have a guaranteed order either. The compatibility comparator treats those five as sets.

- `search_code` redirects to `graphify`, `rg` and `search` (ADR-039); its removal is dated for the next contract version.
