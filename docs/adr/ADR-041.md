# ADR-041: Census of tool-contract consumers and the 2.0 contract window

Status: Accepted.

## Context

The 14-tool contract carries no version (`docs/tools/inventory.md`), and the contract plan splits it into steps: 1.1 is additive apart from three declared removals, 1.2 covers the storage change, and 2.0 covers everything breaking. Two of those decisions depend on who consumes the contract and how:

1. Removing `structuredContent` and `outputSchema` goes into 1.1 only if no consumer reads them; if any does, it moves to 2.0.
2. The 2.0 window is one release (D-H8, confirmed by F5) as long as the inventory check finds no consumers outside the known list: Claude Code sessions, the `ops/contexts/` packages, and Claude Desktop via `mcp-remote` against `acme-drive-knowledge`.

One more question decides whether 1.2 can change the distribution of `score` (RRF) without breaking anyone: whether any consumer applies a threshold to `score`.

## Census

A read-only `rg` search over:

- the 16 packages in `ops/contexts/` (14 from registered repos, `cd-knowledge-mcp` and `_template`);
- the 14 checkouts in `config.json` → `repos`, resolved with the roots in `repos.local.json` (all exist on disk; one more checkout exists and is not registered);
- the Claude Code user configuration (`~/.claude.json`, `~/.claude/{skills,agents,commands,hooks,scripts,output-styles}`, `~/.claude/plugins`), the Claude Desktop one, and that of other clients (`~/.codex`, `~/.cursor`, `~/.config`, `~/Library/LaunchAgents`);
- this repo, excluding `vault/` and `graphify-out/`.

Patterns: the prefixes `mcp__cloudfrog-knowledge__`, `mcp__acme-drive-knowledge__` and `mcp__plugin_*knowledge__`; server names; tool names in skills, hooks, agents, `allowed-tools` and scripts; `structuredContent|structured_content|outputSchema|output_schema`; thresholds on `score` (`min_score`, `score >`, `score <`, `threshold`); and vault path literals (`Work/<vault>`). No header value, bearer or token was read or printed.

The `.mcp.json` files of all packages declare only `memory` and `graphify`: the knowledge server reaches sessions through the user registration, not through the packages. The plugin prefix `mcp__plugin_*knowledge__` appears nowhere. The transcripts in `~/.claude/projects` show real usage from sessions in several of the owner's work and personal repos and in this repo, all through the user registration; the most called tools are `get_document` (59), `search` (37) and `search_by_metadata` (28).

The only `score >= threshold` outside the tests (`scripts/lib/cross_service_edges.py`) is the graph linker's own tier score, not tool output. The `Work/<vault>` literals in the `cloudfrog-saas-api` and `cloudfrog-saas-web` packages belong to skills that read the vault through the `obsidian` MCP server, not through this one.

Outside the known list, only registrations without a target turn up, none of them a live consumer:

- `~/.codex/config.toml` registers `acme-drive-knowledge` over stdio against a local checkout that no longer exists.
- A shell environment file under `~/.config/` defines `CD_KNOWLEDGE_URL` (`:8100`) and a token for the `.mcp.json` of a repo that no longer exists.
- Two AcmeDrive `launchd` agents (vault sync and memory bridge), already documented in `CLAUDE.md`, point to nonexistent checkouts and do not use MCP.
- The `cloudfrog:memory` plugin reads runbooks from the checkout through the file system (`MEMORY_VAULT_ROOT`), not through MCP: no response change affects it.

Census limit: what each client (Claude Code, Claude Desktop, `mcp-remote`, Codex) does internally with `structuredContent` cannot be observed from files. The census covers the code and configuration that read responses.

## Decision

1. **Removing `structuredContent` and `outputSchema` can go into 1.1.** No external consumer reads them; the only reader is this repo's contract test, which is adapted in the same change (re-record the goldens with `KNOWLEDGE_GOLDEN_RECORD=1` and read `content` instead of `structuredContent` in `test_tag_filter_golden_is_not_empty`). Entry condition, because of the census limit: before publishing 1.1, a real Claude Code session against the HTTP server and a real Claude Desktop session via `mcp-remote` answer a `search` and a `get_document` without `structuredContent`, and the result is recorded in the PR.
2. **The 2.0 contract window is one release.** The census finds no consumers outside the known D-H8 list, so there is no reason for the six-month window with per-client telemetry.
3. **1.2 may change the distribution of `score`** (RRF fusion) without declaring it breaking: nobody thresholds it. `score` stays documented as ordinal, not comparable across indexes.
4. **Registrations without a target are cleaned up separately**, without blocking any contract version: the Codex entry, the AcmeDrive environment file and the two `launchd` agents. If someone restores one of those checkouts, the registration becomes a consumer again and enters this census.

## Consequences

- The short 2.0 window depends on the list staying closed: a new consumer (a plugin, another registered client, an `ops/contexts/` package that declares the server in its `.mcp.json`) reopens decision 2. The census is repeated with the commands below before publishing 2.0.
- Removing `structuredContent` cuts the wire size by about half without changing what the model reads (`docs/eval/tokens.md`: the wire/text ratio is around 2 across all tools).

## How to repeat it

```bash
P1='mcp__cloudfrog-knowledge__|mcp__acme-drive-knowledge__|cloudfrog-knowledge|acme-drive-knowledge|knowledge__|mcp__plugin_[A-Za-z_-]*knowledge'
P3='structuredContent|structured_content|outputSchema|output_schema'
rg -n -i --hidden -g '!node_modules' -g '!.git' -e "$P1" -e "$P3" ops/contexts
rg -n -i --hidden -g '!vault/**' -g '!graphify-out/**' -g '!ops/contexts/**' -e "$P3" .
rg -n -i -L -e "$P1" -e "$P3" ~/.claude/skills ~/.claude/agents ~/.claude/commands ~/.claude/hooks ~/.claude/plugins
rg -l -i -e 'cloudfrog-knowledge|acme-drive-knowledge' ~/.codex ~/.cursor ~/.config ~/Library/LaunchAgents
rg -o '"name":"mcp__(cloudfrog|acme-drive)-knowledge__[a-z_]+"' ~/.claude/projects | sort | uniq -c
```

On each registered checkout, run the same `rg` with the patterns above, excluding `node_modules`, `vendor`, `dist`, `build`, `.pnpm-store`, `storybook-static` and `.angular/cache` (third-party code). The names and targets of the servers registered in `~/.claude.json` and `claude_desktop_config.json` are read with a script that prints only name, transport and host, never headers.
