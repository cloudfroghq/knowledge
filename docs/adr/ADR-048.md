# ADR-048: `init` links inside a real `.claude`, what is versioned belongs to the checkout, and `doctor --client` checks only the client

Status: Accepted. Complements ADR-047 (contexts live in each vault and `init` links them on the client) and replaces its direction to use `copy` mode for a checkout with worktrees. This is not a contract change: the contract stays at 2.0.0, no tool changes shape and no golden moves. All that changes is command-line behavior (`init` and `doctor`).

## Context

Context packages are installed only by symlink: the package lives in the vault and each checkout sees it as is, with no copies that drift. The vaults call `init` and `doctor` through their own scripts (`Contexts/scripts/init.sh` and `Contexts/scripts/doctor.sh`, which pin the package version and the vault), and the text the person sees should not name the provider's CLI: each client has its own brand. Two real checkouts do not admit a fully linked `.claude`:

1. **A checkout that stores Claude Code worktrees.** Claude Code creates its worktrees in `<checkout>/.claude/worktrees/` and refuses when `.claude` is a symlink. That `.claude` is a real unversioned directory with an old copy of the package, plus personal `settings.local.json` and `agent-memory/`; its `CLAUDE.md` and `.mcp.json` are old unversioned copies.
2. **A checkout whose repository versions part of its context.** The client's repository versions `.claude/skills/<skill>/SKILL.md` and `.mcp.json`; the vault's package brings a richer `.claude` (`agents`, `commands`, `hooks`, `rules`, `skills`, `settings.json`, `output-styles`, `workflows`…) and its own `.mcp.json`.

The ADR-047 rules solve the first only in `copy` mode, and the second is a conflict that `--force` resolves by setting aside files the repository versions.

## Decision

1. **Link inside a real directory.** In `link` mode, when the checkout already has `.claude` as a real directory (not a link), `init` does not clash with the directory: it plans one relative link for each direct entry of the package's `.claude`, inside the real directory. Per entry: absent, it is linked; already our link to the same target, it is kept; a link that `init` made toward a `Contexts/<package>/` that moved, it is relinked; a foreign link, it is a conflict or is set aside with `--force`; real and versioned, it belongs to the checkout; real and unversioned, it is a conflict, and `--force` sets it aside as `<name>.pre-ai-context.bak-<epoch>` inside the same `.claude`. Nothing is deleted.
2. **A versioned collection also receives entries.** A real `.claude/<collection>/` that the checkout versions (for example `.claude/skills/` with a repository skill) receives, in the same way, the package entries it is missing. It does not go further down: a skill or an agent is a unit, and mixing the files of the repository's version with those of the vault would produce a skill that exists in neither. A real unversioned collection (the old copy of the first case) is a conflict as a whole, and `--force` sets it aside as a whole.
3. **What is versioned belongs to the checkout.** A real entry that git versions in the checkout (`git ls-files --error-unmatch`, which only reads the index) is kept as is with the warning "owned by the checkout": it is not a conflict, does not change the exit code, and the report names it in `actions` and in `detail`. The same rule holds for top-level elements that are files (`CLAUDE.md`, `.mcp.json`), in both modes.
4. **What is personal is never linked or touched.** `settings.local.json`, `agent-memory/` and `worktrees/` are not linked from the package (a vault that once served a linked `.claude` has them in its clone, ignored), and whatever the checkout keeps in its `.claude` that the package does not bring is never touched.
5. **The ignore entries name each link.** `.git/info/exclude` receives `/.claude/<entry>` and its fallback pattern for each link, never `/.claude` when the directory belongs to the checkout, and nothing for what is versioned: a new file the person adds to their `.claude` still shows up in `git status`.
6. **`link` is the only recommended mode.** `copy` keeps working for a vault that declares it, but no case requires it: a checkout with worktrees keeps its real `.claude` and receives the package entry by entry.
7. **`doctor --client`.** For a machine that consumes a remote server, it checks only what belongs to the client: that each vault exists and can be read, that its `Contexts/config.json` loads, the machine's `repos.local.json`, and each checkout according to an `init --dry-run` that neither scans nor prompts (`contexts.checkouts`). It skips what belongs to the server: embeddings provider and key, index, `vector_backend`, judge, memory, bearers, `knowledge_home`, `tool_calls` and `jira` (it names them `skipped`). An absent `repos.local.json` or a checkout yet to be installed is a pending `init` (warning `W_CONTEXTS_INIT_PENDING`, code 0); a checkout that is a git repository without an `origin` remote cannot be verified, but it cannot be proven to be another one either (a clone not yet published): it is the warning `W_CONTEXTS_CHECKOUT_UNVERIFIED` (code 0), and `init` still reports it `unverified` and installs it only with `--force`; a conflict is `E_CONTEXTS_CONFLICT`, and a checkout whose `origin` is another repository, that is not a git repository, or where the package cannot be installed is `E_CONTEXTS_CHECKOUT_INVALID` (code 1); a configuration that does not load, code 2. `--brief` works the same, with the healthy line `knowledge doctor: ok, client, <n> vault(s), default <slug>`, to which `, <n> checkout(s) unverified` is appended when there are `W_CONTEXTS_CHECKOUT_UNVERIFIED` warnings. Without `--client`, the `doctor` report is the same and adds the key `doctor_command`, the command its brief line names on a problem.
8. **One label for the hints.** Every hint that says what to run (the `doctor` brief line, `init.command`, the `W_CONTEXTS_INIT_PENDING` warning, the `_README` of `repos.local.json`, the hint for a conflict or an unverified checkout from `init` and the header of its report) comes from `KNOWLEDGE_COMMAND_LABEL`: `{command}` is replaced by the subcommand (`Contexts/scripts/{command}.sh` gives `Contexts/scripts/init.sh` and `Contexts/scripts/doctor.sh`) and, without it, the subcommand goes after the label. Without the variable, the hints name `cloudfrog-knowledge`, and the one from `doctor --client` adds `--client`; with a label no flags are added, because each script carries its own. A single variable with a placeholder was chosen over two (one per command) because `doctor` names both commands and each script would have to set both. No other environment value appears in a hint.

## Consequences

- The first case is installed by link without `copy`: its `.claude` stays real, Claude Code creates its worktrees there, `settings.local.json` and `agent-memory/` stay intact, and the old copy of each entry (plus the old `CLAUDE.md` and `.mcp.json`) is a conflict until `init --force` sets it aside.
- The second case keeps what its repository versions (`.mcp.json` and the versioned skill) and receives the rest of the package's `.claude`, including the skills its `.claude/skills/` lacks.
- `init` queries git once per real entry it finds, only to read the index; an already installed checkout pays nothing new, and the symlink probe runs only when there is a link to create, so a second run with no changes does not touch the checkout.
- The `_README` of `repos.local.json` names the label: with the default value the text is the same, and an `init` run by a script with a label rewrites that field once.
- Two new codes and one warning, command line only: `E_CONTEXTS_CONFLICT`, `E_CONTEXTS_CHECKOUT_INVALID` and `W_CONTEXTS_CHECKOUT_UNVERIFIED`. No tool returns them.
- Tests in `tests/test_contexts_init.py`, over a copy in `tmp_path` of `tests/fixtures/vaults/contexts/` and checkouts created with `git init`: linking inside a real `.claude`, conflict of an unversioned entry and `--force`, versioned entries, a versioned top-level file in both modes, idempotency, `--dry-run` without writes, relinking an entry toward a vault that moved, `doctor --client` and the hint label.
