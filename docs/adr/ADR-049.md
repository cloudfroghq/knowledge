# ADR-049: each machine chooses in which checkouts `init` installs the context packages (`apply`)

Status: Accepted. Complements ADR-047 (the registry lives in the vault and whatever belongs to the machine lives in `repos.local.json`) and ADR-048 (`init` links inside a real `.claude` and `doctor --client` checks only the client). This is not a contract change: the contract stays at 2.0.0, no tool changes shape and no golden moves. All that changes is command-line behavior (`init` and `doctor --client`).

## Context

`Contexts/config.json` is a vault's shared registry: what each checkout is (id, remote, symbolic root, relative path) and which package corresponds to it. It stores no absolute path; where each root is on a machine lives in `<config home>/knowledge/<slug>/repos.local.json`, outside every vault (ADR-047). Until now `init` installed the package in **every** declared checkout it found on the machine. That does not serve someone who has a checkout cloned and does not want the vault's context in it (they use it for something else, or manage it with another package): the only way out was not to clone it, or to delete the links and watch them come back on the next `init`.

Turning the registry into a per-machine file (a versioned `config.example.json` and the real one ignored) was discarded: the registry holds nothing from the machine, the vault validator and the graph targets read it, and splitting it would make each machine declare again what the vault already declares. What is missing is a per-checkout choice, and that choice belongs to the machine.

## Decision

1. **The selection lives in the machine's file.** `repos.local.json` has a new key, `apply`: the list of registry ids whose packages `init` installs on this machine. It never enters a vault. The file's `_README` explains it.
2. **`init` installs only what is selected.** A present checkout that is not in `apply` is reported `not-selected` with the `--repo ID` hint and is not touched; one that is selected and absent is skipped, as always, and installed when it appears.
3. **Flags.** `--repo ID` (repeatable, `--repo SLUG:ID` for a single vault) adds to `apply`; `--all` adds every present checkout that has a package; `--drop ID` removes the id and deletes only that checkout's links that point to `Contexts/<package>/` (in a real `.claude`, only the entry links; a `copy`-mode copy, the checkout's own files and links, and the ignore entries stay). `--drop` wins over `--repo` and `--all` for the same id. An id that no vault being initialized declares is `E_CONTEXTS_REPO_UNKNOWN`, code 2, writing nothing.
4. **A new machine.** Without `apply`, with nothing to adopt and without flags, `init` asks in a terminal (`all`, `none`, a list of ids, or empty to decide later) and records the answer. With `--yes` or without a terminal it installs nothing, records no choice, and lists the present checkouts with the `--repo ID` and `--all` hint. A `--dry-run` never asks.
5. **Migration with no change for anyone.** The first run on a `repos.local.json` without `apply` creates it with the checkouts that already have their package: links toward `Contexts/<package>/` or, in `copy` mode, a real element that an `init` ignore entry names. Nothing is installed or removed in that run.
6. **What the registry no longer declares is removed.** An `apply` id that the registry no longer declares is removed with the warning `dropped from repos.local.json, no longer declared: apply.<id>`, just like a root or a pin. An `apply` that is not a list of ids is `E_CONTEXTS_INVALID`.
7. **`--dry-run` shows the selection.** The report carries `selection` per vault (`apply`, `previous`, `source` —`overlay`, `adopted`, `prompt`, `flags` or `unset`—, `added`, `removed`, `unselected`), and the text says `would add` and `would remove`; nothing is written.
8. **`doctor --client`.** A present checkout that is not selected is `not-selected`: information, never a problem. One that is selected without its package is a pending `init`, as before. One with links to its package that is not in `apply` is the warning `W_CONTEXTS_LINKED_NOT_SELECTED` (`init` also gives it), and a `repos.local.json` without `apply` is the warning `W_CONTEXTS_SELECTION_MISSING`; both leave the code at 0, and the healthy brief line adds `, <n> checkout(s) linked and not selected` or `, selection missing in <n> vault(s)`.
9. **Only package installation.** `apply` does not change what the registry resolves: the graph targets, `python3 -m knowledge.repos` and the server do not read it, and an HTTP deployment is unaware of it.

## Consequences

- A checkout cloned without the vault's context is possible and stable: `init --drop ID` leaves it clean and no later `init` links it again.
- A machine configured before `apply` stays the same after its first `init`; `doctor --client` warns that the selection is missing until that run.
- A new machine that runs `init --yes` (a script, a hook) no longer receives all the packages: it has to name them with `--repo` or ask for them with `--all`. A vault script that wrapped `init --yes` adds whichever flag it wants.
- One new code and two warnings, command line only: `E_CONTEXTS_REPO_UNKNOWN`, `W_CONTEXTS_LINKED_NOT_SELECTED` and `W_CONTEXTS_SELECTION_MISSING`. No tool returns them.
- A `copy`-mode copy counts for adoption, but not for `W_CONTEXTS_LINKED_NOT_SELECTED`: `--drop` does not delete copies, so warning about them would repeat the warning on every run.
- Tests in `tests/test_contexts_init.py`, over a copy in `tmp_path` of `tests/fixtures/vaults/contexts/`: a new machine with `--yes` and without a terminal, the prompt and each answer, `--repo`, `--all`, a checkout selected before cloning it, unknown ids, `--drop` at the root and inside a real `.claude`, `--drop` over a copy, `--dry-run` of the selection, migration (full and partial), ids that the registry no longer declares, a malformed `apply`, `doctor --client` in each state, and the unchanged registry.
