# ADR-046: Contract 2.0.0: the declared break of the 1.x series

Status: Accepted. Supersedes decision 13 of [`docs/adr/ADR-043.md`](ADR-043.md) (`KNOWLEDGE_STRUCTURED_OUTPUT` at `1` by default) and closes the deferred item of [`docs/adr/ADR-042.md`](ADR-042.md) on structured output. Contract in `docs/contract/CHANGELOG.md`, section 2.0.0; measurements in `docs/eval/tokens.md`, section "Contrato 2.0.0" (that file is in Spanish; the heading means "Contract 2.0.0").

## Context

The 1.x series grew additively: no tool lost a key, no default moved and no tool disappeared. Everything that would have broken a client was left in the "Deferred" rows of 1.1.0 through 1.4.0 with the destination "2.0": structured output by default, `export_hint`, the unrounded `weight` of `get_related`, unbounded lists, the `{"error": …}` objects that respond as success, the removal of `search_code`, and the extension tools that register even when no vault declares them.

2.0.0 resolves those deferred items in a single version, with each change declared: an `R<n>` row under "Breaking" in the CHANGELOG and a rule with the same id in `MIGRATIONS_2_0` (`tests/golden_compat.py`). The 1.4.0 goldens, migrated by those rules and only by them, are compared key by key with what 2.0.0 answers; whatever no rule names comes back with the same value.

## Decision

1. **The canonical response is the text** (R19). `KNOWLEDGE_STRUCTURED_OUTPUT` becomes `0` by default: no response carries `structuredContent` and no tool declares `outputSchema` unless the operator turns the variable on. With `1` the structured view comes back, which is the same JSON as the text blocks (`test_structured_output_on_only_adds_the_structured_view`). No 2.x client may depend on that view, so turning it off or on within 2.x is not a version change.
2. **`snippet` does not become a default.** The default row of `search` and `search_deep` carries pointers (`chunk_id`, `section`), not an excerpt. With `text-embedding-3-large` over the fixed corpus, the 120-character excerpts of the five rows cover the answer in 1 of 50 queries and cost 191 tokens per search; with 400 characters they cover 14 for 571. Nor do they help choose what to read: the first row is the main document in 36 of 50 queries, and a reader who chooses by the words in the excerpt gets it right in 30 to 35. `excerpt` and `snippet` stay on request.
3. **`chunk_id` and `section` travel by default; `doc_id` stays on request** (it is encoded inside `chunk_id`). `search_deep.discovered_via` does not change to `doc_id`: without `doc_id` in the row, the agent could not resolve the reference.
4. **`get_document`** reads 3,000 characters by default, returns metadata on an allowlist (`type`, `status`, `service`, `owner`, `tags`, `last_updated`) except with `full_metadata=True`, and accepts `chunk_id` without `file_path`. `include_metadata` is retired with an error (R20) instead of being removed from the schema, because the SDK silently drops an argument the schema does not declare.
5. **Every list has an upper bound** and every `limit` has a cap; out of range is `E_ARGUMENT_OUT_OF_RANGE`.
6. **Every tool error is `isError: true` with a text containing `E_<CODE>: <message>`**, preceded by the SDK's `Error executing tool <tool>: ` except for `E_TOOL_RETIRED` and for `E_FEATURE_DISABLED` of a tool the process does not register, which the server answers without reaching the tool: the `{"error": …}` objects that responded as success become codes (`E_FILE_NOT_FOUND`, `E_SECTION_NOT_FOUND`, `E_FILE_NOT_IN_GRAPH`, `E_FLOW_NOT_FOUND`, `E_SECRET_MISSING`, `E_SCOPE_EMPTY`). Two error objects that live inside a report and are not the entire response remain rows: `errors[].error` of `sync_confluence` (a file that could not be compared) and the `error` with a code in `sync_jira` when memory fails midway through a run, next to the counts of what it did write.
7. **Gated extensions.** `flows`, `governance` and `confluence` register their tools only when some served vault declares them, like `jira`. `needs_review` and `age_days` remain in the rows of every vault: the server imports `knowledge.review` at startup, and `gated` only conditions `get_stale_docs` and `suggest_links`. In a process with several vaults, calling an extension tool on a vault that does not declare it is `E_FEATURE_DISABLED`, and the message names the vaults that do declare it. The team vault keeps `features: [governance, git-webhook]`: declaring `confluence` in an HTTP deployment without its credentials would stop startup.
8. **`search_code` leaves the `all` profile.** Calling it responds `isError` with `E_TOOL_RETIRED` and the same redirect as ADR-039 (graphify, `rg`, `search`); an extension tool that no vault loads responds `E_FEATURE_DISABLED`, not the SDK's "Unknown tool". A client with the 1.x catalog cached receives an actionable message. Under `legacy` its `_meta` announces removal in 2.1.0 (R21), not in 2.0.0 as 1.1.0 through 1.4.0 said.
9. **`legacy` profile for one release**, chosen with `serve --profile legacy` or `KNOWLEDGE_PROFILE=legacy` (the flag wins; any other value is `E_PROFILE_UNKNOWN`, exit code 2): the catalog with the names and order of 1.4.0, the extension tools always registered and `search_code` in its position, with the 2.0 schemas and responses. `all` remains the default. No `knowledge-legacy` entry is published in the marketplace: nobody has the `knowledge` plugin installed, a second name would change the prefix of the tools the skills list, and two stdio processes over the same index would compete for its lock. The window is served with the `v0.5.0` tag, installable via `uvx`, and with this profile.
10. **2.0 `instructions`** with the two-step protocol (`search(query)` and `get_document(chunk_id=…)`, or `get_document(file_path)` when the row carries `chunk_id` as `null`), 368 characters. The rule for removing `max_chars` from the text (default 2.0 flow at no more than 900 tokens on average and with coverage no lower than the 1.4.0 protocol's) is met: 873 tokens and 30 of 50 queries versus 794 and 27.
11. **`reindex` does not `git pull` by default** and does not return `export_hint`; the webhook brings the vault on every push. The recovery line in `CLAUDE.md` becomes `reindex(force=true, pull=true)`. `sync_confluence` loses `space_key` and `page_id`, which it had ignored since 1.3.0.
12. **Call telemetry.** The server counts calls per tool, client (`clientInfo.name`) and principal (the bearer's id, never the token) in the `tool_calls` section of `usage_stats.json`, with 120 days of retention, without arguments or queries, and `doctor` shows it. It entered `main` separately, with no contract change, so that the team deployment counts calls while serving 1.4.0. That count is the evidence for removing `legacy`: zero calls to `search_code` in the window, except the logged probes.

## Deviations from the plan

The version plan asked for something else on five points; the owner approved each deviation:

| Plan | 2.0.0 | Why |
|---|---|---|
| `snippet` in the default row | Pointers by default, `snippet` on request | Decision 2: the excerpt costs more than it avoids |
| `discovered_via` as `doc_id` | No change | Decision 3 |
| Per-tool errors according to each case | Every tool responds `isError` with a code | Decision 6: a single error shape |
| A `knowledge-legacy` entry in the marketplace | `legacy` profile in the same package, by flag or variable | Decision 9 |
| `get_document` always with `file_path` | `chunk_id` alone is enough | Decision 4: the two-step protocol reads what the row names |

And one that the plan left for a later 2.x: `KNOWLEDGE_STRUCTURED_OUTPUT=0` by default enters 2.0.0 as a declared breaking change (R19), with the evidence in the next section.

## Evidence for structured output

ADR-042 conditioned the `0` default on two real sessions without `structuredContent`: one from Claude Code and one from Claude Desktop via `mcp-remote`. The Desktop one was run with a local stdio server at `0` and with the remote deployment at `1`; the `mcp-remote` path at `0`, the one used by AcmeDrive clients, remains unverified (Deferred).

- **Claude Code** (ADR-043, decision 13): passes with `0` and with `1`. With `1` the client hands the model the `structuredContent`; with `0`, the text blocks, and the session answers the same.
- **Claude Desktop for macOS**: the owner ran it on 2026-10-13 (UTC) with two calls, a `search` with `limit` 3 on "cómo se despliega el SaaS" (how the SaaS is deployed) and a `get_document` of the CI/CD note in the team vault with the `chunk_id` of the first result and `max_chars` 1500, against two contract 1.4.0 servers:

| Server | `KNOWLEDGE_STRUCTURED_OUTPUT` | `search` | `get_document` |
|---|---|---|---|
| Team deployment over HTTPS, with the `jev` judge | `1` | Three rows with `file_path`, `title`, `score` and `excerpt` (and `rerank_score` on the two the judge read), which the interface shows field by field and the model summarizes | The model notes that the row carries no `chunk_id` (it does not travel by default in 1.4.0) and that the requested document is not the first result, and reads the document by `file_path` with `max_chars` 1500: metadata and truncated text, with `next_offset`, which it summarizes and offers to continue |
| Local stdio `cloudfrog-knowledge` 0.5.0, without a judge (its vault clone does not declare `rerank`) | `0` | Three rows with the same fields, shown the same way; the model summarizes them the same way | The model repeats the search with `fields` (`chunk_id`, `section`) to get the pointer, reads the section with `chunk_id` and `max_chars` 1500 and summarizes it; it offers to continue with `next_offset` |

What the session proves: with `0`, Claude Desktop shows the rows the same as with `1` (it reads the JSON in the text blocks) and `get_document` is usable, including reading by `chunk_id`. What it does not prove: content equality between the two columns, because the two servers do not serve the same thing (the deployment reorders with the judge and its first row is `Docker & Deploy.md`; the local one, without a judge, puts `CI-CD.md` first, and its vault clone is older: the frontmatter of `CI-CD.md` carries `last_verified` where the deployment carries `last_updated` and `verified_against`); and reading by `chunk_id` with `1`, which the session with the deployment never got to do. Nor does it distinguish reading by `chunk_id` from reading the whole document: `41e005a22d:1` is the H1 block of `CI-CD.md`, which spans the whole document, and it returned the same 1,500 characters and the same `next_offset` as the `file_path` read in the first case. The model also matched the rows of the second search to those of the first by position, which breaks if the order changes between calls (each `search` adds usage). That the model had to repeat the search to get the `chunk_id` is what R1 fixes: in 2.0.0 the default row carries it. The transcript lives outside the repository, without the bearer or paths from the owner's machine.

With this evidence, decision 13 of ADR-043 is superseded: the change to `0` is a contract version with its row under "Breaking" (R19), as ADR-043 asked, but in 2.0.0 and not in a later 2.x. The 1.2.0 deferred item ("2.0 at the latest") closes on time. The saving is on the wire: the 38 responses that 1.4.0 and 2.0.0 record under the same name go from 14,567 to 7,431 wire tokens (−49 %), and the main session's catalog from 7,527 to 6,294 bytes. In Claude Code the context barely changes, because the client hands the model one view or the other, of the same size (6,527 text tokens versus 6,336 of `structuredContent` in the 1.4.0 goldens); that equality was not measured with `/context`.

## Measurement

Over the fixed corpus of `docs/eval/tokens.md`, with `text-embedding-3-large` and `rerank="off"`, each session over its own copy of the same index without usage history or learned weights; version 1.4.0 with the code of the `v0.5.0` tag:

| Measure | 1.4.0 | 2.0.0 |
|---|---|---|
| recall@5 · MRR@5 (50 queries) | 0.930 · 0.897 | 0.930 · 0.897, same five paths in the same order in all 50 |
| default `search` (tokens per query) | 354 | 236 (−33 %) |
| Default `search → get_document` flow | 1,604 tokens, coverage 24 of 50 | 873 (−46 %), coverage 30 of 50 |
| 1.4.0 protocol (`fields`, `chunk_id`, `max_chars=2000`) | 794, coverage 27 of 50 | 760, coverage 27 of 50 |
| Catalog, `tools/list` wire without `outputSchema` | 16 tools, 8,887 B · 2,082 tokens | 10 tools, 6,294 B · 1,500 (fixture and personal vault); 12 in the team vault |

Both versions read the same `config.json` (review thresholds per type): the 1.4.0 one receives it through `KNOWLEDGE_CONFIG_JSON`, because the tag's code loaded via `PYTHONPATH` does not find the repository's and would fall back to the single 270-day threshold. A 2.0.0 measurement session passed it to only one of the sides, and in 10 of 50 queries the 2.0.0 row carried `needs_review` and `age_days` that the 1.4.0 one omitted; repeated with the same `config.json`, 1.4.0 rises from 352 to 354 tokens per `search` and from 1,602 to 1,604 per flow, and the rows, the `score` values and the recall do not change (recall@5 0.930 and the same five paths in all 50 queries). The recall with `text-embedding-3-large` was measured in the measurement session and repeated with the symmetric configuration.

The catalog is labeled as wire: in Claude Code with tool search the MCP schemas are loaded on demand, so removing tools saves bytes and the cost of loading them, not context tokens at startup. The nine sessions embedded only queries, about 9,000 tokens: USD 0.0012.

## Parent branch

The team deployment is rebuilt on every push to `main`. A loose breaking change on `main` would leave that deployment serving a half-done contract, so 2.0.0 is assembled on a parent branch, `feature/contract-2-0`, which reaches `main` in a single merge; only the call telemetry, which is additive, entered `main` separately. This is an exception to `.claude/rules/git.md`, which asks for branches from `origin/main` and merges to `main`: the owner's global rule (a subfeature is merged into its parent feature) covers it, and the reason is the auto-deploy. The `.claude/` skills that read shapes that change are adjusted on the same parent branch, so that server and skills land together.

**Rollback**: `git revert -m 1 <parent branch merge>` on `main`. The auto-deploy goes back to serving 1.4.0 with the call telemetry included, and the revert undoes the skill changes in the same commit. Going back to a commit without the telemetry would delete the `tool_calls` section on the first save of `usage_stats.json`. A `vault.yaml` that declares `knowledge_contract: ">=2.0,<3"` served by 1.4.0 only produces the `W_CONTRACT_RANGE` warning; it never stops startup.

## Deferred

| Point | Why | Goes to |
|---|---|---|
| `snippet` by default | 1 of 50 coverage with 120 characters and +191 tokens per search (decision 2) | If a measurement with embeddings shows at least 30 % of reads avoided with no more than +100 tokens |
| `discovered_via` as `doc_id` | ~10 tokens per hop row | If `doc_id` reaches the default row |
| Confluence importer into a derived index (`imported`, admin scope) | `sync_confluence` stays read-only (ADR-044); importing requires a separate index and its own write boundary | A 2.x version with its own design |
| Single-facet filter in `search_by_metadata` | Facets are paginated like rows | If facet pagination proves awkward in use |
| `total` in `get_related`, `suggest_links` and `get_stale_docs` | Lists already bounded by `limit` | With evidence of truncation in use |
| `serverInfo.version` with the package version | Today it is the `mcp` SDK's | With the migration to `mcp` 2.x |
| Claude Desktop via `mcp-remote` with `KNOWLEDGE_STRUCTURED_OUTPUT=0` | The owner's session used a local stdio at `0`; `mcp-remote` is the path of AcmeDrive clients | As a condition for moving the AcmeDrive deployment to 2.0.0, with the ADR-042 procedure; if it fails, that deployment sets the variable to `1` |
| Reading by `chunk_id` in Claude Desktop with `KNOWLEDGE_STRUCTURED_OUTPUT=1` | The owner's session did it only with `0` | If a deployment turns on the structured view for a desktop client |
| Removal of the `legacy` profile and of `search_code` | Lives for one release | 2.1.0, with the window's telemetry at zero |

## Consequences

- A client that passes no parameters receives rows with pointers, bounded reads and errors with codes; the `search` → `get_document(chunk_id)` flow is the one taught by `instructions` and the `search-first` skill, and it costs 873 tokens per question instead of 1,604.
- Personal and Initech stop seeing `get_flow` and `compare_flows`; personal also loses `get_stale_docs` and `suggest_links`. Getting them back means declaring the extension in their `vault.yaml` by human PR.
- The row's pointer is chosen by `pointers.select_section` from the query words in the document's headings; it is not the chunk that ranked. Over the fixed corpus with `text-embedding-3-large` and `rerank="off"`, in the 250 default rows of the 50 queries: none carries `chunk_id` as `null`; 74 point to an H1 block that spans at least 90 % of the document (16 of the 50 first rows), and there reading by `chunk_id` costs the same as reading the document; and in 119 the excerpt of the chunk that ranked falls outside the block the row points to. With a judge (`rerank`), the row names the block the judge read.
- Whoever calls `reindex` expecting a `git pull` receives `vault_sync: skipped_pull_false` and has to ask for `pull=true`.
- Each 2.0.0 golden is recorded with the text as the only response; the `structured` session proves that the structured view is the same JSON.
