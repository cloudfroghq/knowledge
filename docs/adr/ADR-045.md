# ADR-045: The `Judge` port and `search` rerank with the vault's judge (contract 1.4.0)

Status: Accepted. Numbers in `docs/eval/rerank.md`; contract in `docs/contract/CHANGELOG.md`, section 1.4.0.

## Context

`search` sorts by a hybrid fusion (`0.7 · cosine of the best chunk + 0.3 · normalized BM25`, times the usage boost). On the team vault's 50-query set it almost always finds the documents (recall@20 0.993), but it does not always put them first nor point to the section that answers: hit@1 0.80, and reading row 1 with its `chunk_id` covers the answer in 23 of 50 queries (0.46). The headroom is in the order and in the section, not in coverage.

Section 9.5 of the master plan asked for a rerank with an external judge, opt-in per vault, with a gate of **+10 points of precision@5** and **p95 ≤ +500 ms**. Section 11 fixed the parameter as `rerank?: none | jev | local`. A pilot measured 16 variants (judged unit, number of candidates, request shape, fusion, conditional cut, Jev versus local Kev) over those same 50 queries.

## Decision

1. **`Judge` port in the core** (`src/knowledge/ports.py`): `JudgeUnit`, `JudgeVerdict`, `JudgeUnavailable` and `NullJudge`. Each vault composes its judge in the registry (`VaultRuntime.judge`); without a `rerank` block in its `vault.yaml` the judge is `NullJudge` and `search` is that of 1.3.0 byte for byte.
2. **A single System One adapter for `jev` and `kev`** (`src/knowledge/judges.py`, ext layer, `rerank` extension of the `extensions.py` registry, loaded by the server's only by-name loader). Jev and Kev speak the same API; two classes would be the same class. Standard library: a persistent `http.client.HTTPSConnection` per thread (never a global lock), one reconnection when the provider closed a connection, a TLS connection opened in parallel with the query embedding, a total deadline with `future.result(timeout)` that covers DNS, a body of up to 256 KB, no proxy and no redirects. The `jev` URL is fixed (`https://api.typesafe.ai/v1/systemone`); `kev` accepts only loopback. `uv.lock` does not change: neither `typesafe-sdk` nor a `[judge]` extra.
3. **The judged unit is the pointer block**: what `get_document(file_path, chunk_id=…)` returns, cut to 2,000 characters. Up to 2 per document (the one under the heading of the best dense chunk and the one that weighs most for the query), over the first 10 documents of a *pool* of `fetch = 2 · max(limit, 20)` chunks per path.
4. **One request per query**, with one `noul` question per block (`candidates[i]`) and the versioned model (`jev-1.13.0`, never the `jev-latest` alias, which changes without notice).
5. **Bounded fusion, not replacement**: `score = round(hybrid · boost · (0.8 + 0.5 · p), 2)`, with `p` the best probability among the document's blocks; a document the judge did not see keeps its `score`. `score` remains ordinal (it can exceed 1); `rerank_score` is the probability of the chosen block. When requested, `chunk_id`, `section` and `snippet` name the block the judge chose.
6. **Always, not conditional**: `rerank.conditional_gap` exists with `null` by default.
7. **A judge failure is never `isError`**: 1,500 ms deadline, circuit breaker (3 consecutive failures open it for 60 s; a rejected key, for 15 min), per-request token budget and a USD cap per day and vault, shared across processes through `usage_stats.json`. The response is the search without a judge, with the reason in `_meta["knowledge/rerank"]`. Only an impossible configuration (`rerank="on"` in a vault without a provider) is `E_RERANK_NOT_CONFIGURED`.
8. **Privacy by manifest**: content leaves for TypeSafe only if the `vault.yaml` (curated content, human PR) declares `rerank.provider: jev`. The operator turns it off (`KNOWLEDGE_RERANK=off`) or restricts it (`KNOWLEDGE_RERANK_PROVIDERS`); a call argument never enables a provider the vault does not declare; `never_send` excludes prefixes; with `include_memories=True` or a mode other than `hybrid` there is no judge. The key is named per vault (`TYPESAFE_API_KEY` only in the default vault, `<PREFIX>_TYPESAFE_API_KEY` in any) and never appears in the manifest, a log, an error or a response.
9. **Parameter `search(..., rerank=None | "off" | "on")`**, at the end of the signature: omitted, it follows the vault's `rerank.default`. Contract 1.4.0, additive.
10. **On by default in the owner's vaults**: the four vaults (`cloudfrog`, `acme-drive`, `initech`, `personal`) declare, by human PR, `rerank: {provider: jev, default: on, model: jev-1.13.0, candidates: 10, units_per_doc: 2, timeout_ms: 1500, max_input_tokens: 20000, max_usd_per_day: 1.00, conditional_gap: null, never_send: []}`, and `key_env` with the prefix of its slug (`CLOUDFROG_TYPESAFE_API_KEY`, `ACME_DRIVE_TYPESAFE_API_KEY`, `INITECH_TYPESAFE_API_KEY`, `PERSONAL_TYPESAFE_API_KEY`), which holds whether or not it is the default vault of the process that serves it: an unprefixed `TYPESAFE_API_KEY` in a vault that is not the default is a fatal startup error. The package without a `rerank` block stays on `NullJudge`. A vault with `default: on` and a missing key starts anyway, over stdio and over HTTP: warning `W_RERANK_KEY_MISSING` and search without a judge (`reason: key_missing`). A deployment that updates only from `main` never exits with code 2 for not having the key yet.

## The section 9.5 gate, amended

**+10 points of P@5 is unreachable with these labels.** With 1 to 3 expected documents per query, the P@5 ceiling of the 50-query set is 0.356: from the 0.324 baseline the entire headroom is +3.2 points, whatever the judge does. Read as +10 % relative (0.356), it requires a perfect ranking. The gate keeps the plan's metric, but as a fraction of the headroom, and adds floors against noise, over two sets:

| Criterion | Tuning set (50) | Control set (36) |
|---|---|---|
| P@5 ≥ base + (ceiling − base) / 3 | 0.324 → **0.340** (threshold 0.335) | 0.289 → **0.328** (threshold 0.317) |
| hit@1 ≥ base + 0.06 | 0.800 → **0.920** (threshold 0.860) | 0.611 → **0.833** (threshold 0.671) |
| MRR@5 and nDCG@5 do not drop in any language | MRR 0.897 → 0.955; nDCG 0.870 → 0.929; no language drops | MRR 0.728 → 0.890; nDCG 0.702 → 0.861; no language drops |
| end-to-end `search` p95, per MCP client, ≤ base + 500 ms, with the rule below | 462 → 754 ms, **+293 ms** (5 runs per mode, 250 searches; macOS) | 482 → 800 ms, **+318 ms** (5 runs per mode, 180 searches; macOS) |

**It is met on both sets.** Quality, in all the macOS runs with a judge and in the Linux one; latency, with the reading rule below, committed (commit "docs(adr): fix the rule that reads the p95 gate before measuring it") with no confirmation run done. The measurement in a Linux container on the same computer is not independent (same network and same egress to TypeSafe) and the latency from the `:8200` host is pending: the gate is not declared met there until it is measured. The table's baseline is `rerank="off"` over a clean copy of the index; with the production baseline from the decision (P@5 0.320, hit@1 0.82) the tuning-set thresholds become 0.332 and 0.88, and are also met. The control set (36 queries, 19 es and 17 en) exists because the configuration was chosen by measuring variants over the 50-query set: measuring only there reproduces the tuning, it does not validate it. It was written by reading the contents of `cloudfroghq/vault`, frozen with its sha256 in `ops/eval/README.md` and committed before any run with a judge had read it. On that set the improvement in MRR (12 queries improve, 3 get worse, p = 0.035) and in hit@1 (10/2, p = 0.039) is significant at 5 %; on the 50-query set it stays at p = 0.07 (7/1), because 40 of those 50 queries already had the expected document at position 1. Reading row 1 improves on both: cover@1 0.46 → 0.66 (10/0, p = 0.002) and 0.19 → 0.50 (11/0, p = 0.001).

### How the p95 is read

The latency gate is read with a fixed rule, written in this ADR and committed with no run done to confirm it:

- Per query set and environment, 5 runs per mode (`rerank="off"` and `rerank="on"`), alternated, each over its own clean copy of the index and with a warm-up search outside the clock (`scripts/eval_retrieval.py --warmup 1`): the first search of a process pays the connection to OpenAI and to TypeSafe and does not measure the judge's cost.
- The p95 of each mode is computed over all its searches together (5 runs × the set's queries). The gate is met if `p95(on) − p95(off) ≤ 500 ms` on each set.
- The p95 difference by run pairs (each run with a judge against each run without) is published as dispersion and does not decide: with 36 or 50 queries the p95 of one run is the second or third highest value and a single slow search moves it.
- A measurement on the same machine, even inside a Linux container, is not independent: it shares the network and the egress to TypeSafe. The latency that counts for a deployment is measured from its host.

## Deviations from the plan

| Plan | What it said | What was decided | Why |
|---|---|---|---|
| 9.5, gate | +10 points of P@5 and p95 ≤ +500 ms | Fraction of the P@5 headroom (1/3), hit@1 +0.06, MRR and nDCG not dropping per language, p95 ≤ +500 ms, over two sets | The P@5 ceiling makes +10 points unreachable (see above) |
| 9.5, unit | Snippet of up to 700 characters | Pointer blocks of up to 2,000 characters, 2 per document | With the first 700 characters of the best chunk the judge sinks the ranking (MRR 0.895 → 0.611 in the pilot): it judges a passage that does not contain the answer even though the document does |
| 9.5, shape | Noul fan-out, one request per candidate | One request per query with one question per block | Jev bills ≈290 fixed tokens per request; fan-out in a single request costs 30 % less and performs the same or better |
| 9.5, candidates | Top-20 | 10 documents (1 to 12) | 10 performs the same as 20 with half the tokens; with 20 the request is around 25,000 tokens and the judge's p95 rises to 430-450 ms |
| 9.5, condition | Conditional rerank by default | Always, with optional `conditional_gap` | The cut by gap < 0.03 fires on 13 of 50 queries and loses most of the gain (MRR 0.963 → 0.943 in the pilot); at USD 0.0005 per query the saving does not compensate |
| 9.5, client | `typesafe-sdk` | Standard library | The SDK raises `idna` and adds 5 distributions to the lock and the image; its retry with backoff is no good with a 1.5 s deadline on the path of every search |
| 11, parameter | `rerank?: none \| jev \| local` | `rerank: "on" \| "off"` (omitted follows the vault) | The provider decides where the vault's content travels: the vault declares it and the operator allows it, not the caller. The 1.x series inherits `on|off` |
| 11, `local` provider | Local cross-encoder | Deferred | See below |

## Why pointer blocks and not the index chunks

- **Addressability.** The agent reads `get_document(file_path, chunk_id=…, max_chars=2000)` after searching. The pointer block is exactly that text, so the judge judges what the agent is going to read, and the row's `chunk_id` and `section` name it. The index chunks (up to 2,500 characters, 10 % overlap, cut by `## `) are not addressable by `chunk_id`: if the judge chose a chunk, the agent could not request that text. Measured in the reading flow: with the judge's block, reading covers 33 of 50 queries against 27 without a judge, for 785 flow tokens against 794.
- **Cost per query.** With the same 10 documents and up to 2 units, the blocks bill 11,668 tokens per query (USD 0.00049) and the full chunks 13,317 (USD 0.00056) in the pilot; the official measurement gives 11,743 tokens and USD 0.000493.
- **Quality.** Full chunks perform slightly better on MRR in the pilot (0.975 versus 0.963), but their reading coverage is not reachable by the agent (the chunk the judge preferred cannot be read by pointer). The block trades a fraction of MRR for a reading that does answer.

## Deferred

- **Local cross-encoder** (the `local` provider of section 11): requires downloading a model (`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1` via fastembed), which needs the owner's approval. It was neither downloaded nor measured: without a number it does not compete for the default. If approved, it enters as a provider of the same port with its own gate (disk size, RSS, p95 ≤ +500 ms on Linux and the metrics in `docs/eval/rerank.md`).
- **Kev as an option without egress, not as the default.** Local Kev-4B speaks the same API, so it is the same adapter with `provider: kev` and a loopback `base_url`: no content leaves the machine. Measured in the pilot, it performs above the baseline (MRR 0.918 with the same units) but below Jev (0.963) and takes 5.4 to 12.6 s per query: it does not suit the `search` path; it does suit a vault that forbids egress and accepts seconds, or batches. In the suite and in the goldens the judge is a deterministic System One double on loopback (`tests/systemone_fakes.py`), never Jev or Kev.
- **Batch governance judges** (duplicates, stale notes): without a labeled set, the judge contributes no finding that cosine does not already give (1 duplicate with `noul` > 0.8 in 80 pairs, already discarded).
- **Rerank in `context_pack` and `search_deep`**: unchanged in 1.4.0; they open when a `context_pack` measurement with a judge covers at least +0.08.
- **Persistent on-disk cache**: the cache lives in memory per process; it is reopened with the real `cache_hit_rate` from `doctor`.

## Risks

| Risk | Mitigation |
|---|---|
| Egress of vault content to TypeSafe | Only with `provider: jev` in the `vault.yaml` (human PR), `never_send`, never memories, operator switch. Jev does not train on requests; zero retention only on enterprise plans |
| Key leak | Name per vault, fixed URL, `kev` only on loopback, no proxy or redirects, `repr` without the key; the tests require that the key not appear in logs, errors or responses |
| TypeSafe latency and outages | 1.5 s total deadline, circuit breaker, response without a judge with its reason. Measured: median +249 to +267 ms; the judge under 500 ms in 437 of 440 calls of the confirmation (3 between 500 and 1,000 ms); 0 failures or expired deadlines in 748 calls |
| Latency from the deployment | The Linux container of the measurement runs on the same computer as macOS, with the same network and the same egress to TypeSafe: it is not an independent measurement. The latency from the `:8200` host, where the team vault serves `default: on`, is pending: it is measured from that host with the key loaded before the gate is considered met there. Without the key, that deployment searches without a judge (`key_missing`) and pays no latency |
| Double retrieval when the judge is not applied | If the rerank is evaluated and not applied for a reason known only with the *pool* (`breaker_open`, `budget_day`, `budget_tokens`, `gap`, `no_candidates` or a judge failure), `search` retrieves the 20-document *pool* and then repeats the `limit` search, so that the rows are exactly those of the search without a judge. The second retrieval reuses the query embedding (process cache) and is one local FTS5 query plus one local KNN. With the circuit breaker open it is kept on purpose: blocks already in cache keep answering without calling the provider |
| Jev non-determinism | Two runs per set: row 1 matches in 86 of 86 queries and no metric differs by more than 0.02. The cache stores the first response; no golden depends on Jev |
| Small sets | 50 + 36 queries; one query moves hit@1 by 0.02-0.03. That is why the gate requires the control set and per-language floors |
| Cost from abuse with a read bearer | `max_usd_per_day` per vault shared across processes, per-request token budget, `doctor` shows it |

## Consequences

- Additive contract 1.4.0: without `rerank` requested or `default: on`, every response is that of 1.3.0. With the owner's vaults on `default: on`, `search` reorders without the caller asking and `_meta["knowledge/rerank"]` says what the judge did.
- `scripts/eval_retrieval.py` gains `--rerank`, `--cover`, `--pass-env` and the metrics hit@1, prim@1, nDCG@k and cover@1; `scripts/measure_tokens.py --flow` gains `--rerank` and `--pass-env`. Changing `model` in a vault requires measuring the new Jev version with `docs/eval/rerank.md` over both sets.
- A control set with its hash lives in `ops/eval/cloudfrog/queries-holdout.yaml`; it is not edited after measuring.
