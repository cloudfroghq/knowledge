# ADR-043: Contract 1.2: one SQLite file per vault, with the ranking measured

Status: Accepted. Extends the ADR-042 rule to the values that come out of the ranking and amends ADR-042 at one point: the value of `export_hint` in `reindex`.

## Context

In contract 1.1.0, each vault is served from a Chroma collection plus three JSON files next to it (`keyword_index.json`, `link_graph.json`, `usage_stats.json`). Chroma brings more than 90 MB of dependencies, an approximate HNSW index and a filter dialect (`where`) that the server uses in six forms. The lexical part of that hybrid search is an in-memory TF-IDF over the whole document, independent of the chunks.

Contract 1.1.0 promises values, as parsed JSON, against its goldens. A storage change moves `score`, order and row membership in the three tools that sort by the index (`search`, `search_deep`, `context_pack`) even though no key or parameter changes.

## Decision

1. **One SQLite file per vault** (`index.sqlite`, `index_version` 1 format): one row per document with its frontmatter and body, its chunks, an FTS5 index (`unicode61 remove_diacritics 2`) and its float32 vectors. With the `sqlite-vec` 0.1.9 extension, a `vec0` table answers exact KNN with `k = ?`. Without it (a Python without loadable extensions), the same vectors are sorted by brute force with the standard library: `vector_backend: python` in `doctor` and `/health`, with the same result except for exact similarity ties at the `k` boundary (`vec0` chooses among the tied ones in its own order; the fallback breaks ties by `file_path` and chunk number), about 110 ms per query with 1,480 vectors of 3,072 dimensions versus about 10 ms with `sqlite-vec` (median of 20 queries on an Apple M2 Max, Python 3.12.12, SQLite 3.50.4). A process that does load the extension rebuilds the `vec0` table before querying it when another process wrote vectors without it. `KNOWLEDGE_REQUIRE_SQLITE_VEC=1` turns that fallback into the `E_SQLITE_VEC_UNAVAILABLE` error; the pipeline and the golden recording use it. The plugin launches the server with `uvx --managed-python`, so that it runs on a `uv` CPython, which loads the extension.
2. **The ports leave the Chroma dialect.** `ChunkFilter` is a closed filter with the predicates the tools use (paths, equality on `type`/`service`/`status`, excluded types and prefixes, a tag); reads return typed records (`DocRecord`, `ChunkRecord`, `ChunkHit`). `InMemoryVectorStore` implements the same port with a BM25 that follows the FTS5 arithmetic, and the `tests/test_stores.py` suite requires both stores to return the same paths in the same order and the same `score` with `rel=1e-6`.
3. **The lexical side of the hybrid search is FTS5 BM25 per chunk**, chosen by measurement with a rule fixed in the design: FTS5 stays if its recall@5 does not lose more than 0.010 against TF-IDF on the same index and reaches 0.890. With `text-embedding-3-large` over `vault/cloudfrog` (50 queries, same index, two clean copies): FTS5 0.930 (MRR@5 0.897), TF-IDF 0.920 (MRR@5 0.869). With `none`: FTS5 0.837 versus 0.803 for TF-IDF. The fusion does not change (`0.7·semantic + 0.3·lexical`, normalization by the maximum, tie-break by `file_path`): reciprocal rank fusion lost in 13 of 15 configurations of the sweep (`docs/eval/sweep.md`).
4. **The section selector of the pointers does not change.** `chunk_id`, `section` and `snippet` still come from the body on disk with the usual per-substring idf, computed from the bodies stored in the index (`(empty)` for an empty body), so they do not depend on the store.
5. **Contract 1.2.0 rule:** additive in keys, parameters and defaults, like 1.1.0; the values that come out of the ranking stop being stable across indexes and each golden that changes has its row in "Changed (non-additive)". `tests/golden_compat.py` compares those three tools by shape against 1.0.0 and 1.1.0, and all the others by value.
6. **Amendment to ADR-042, `export_hint` row.** ADR-042 keeps `export_hint` identical until 2.0, with the removal of `scripts/export-data.sh`. That script packages a Chroma index that the server does not read and is removed in this version, together with `chromadb`, so the 1.1.0 text points to a path that does not exist. In 1.2.0 the **key** is kept (removing it is still a 2.0 matter) and its **value** becomes `"The index rebuilds from the vault; no export is needed"`, declared in "Changed (non-additive)".
7. **Where the index lives.** In a `VAULT_PATH` deployment, the index directory is the first of `KNOWLEDGE_INDEX_DIR`, `CHROMA_PERSIST_DIR`, `<KNOWLEDGE_HOME>/<slug>` (only with an explicit `KNOWLEDGE_HOME`) and `<root>/.data/<slug>`; in a `vaults.yaml`, `<data_dir>/<slug>`. `CHROMA_PERSIST_DIR` remains a destination on purpose, and the image sets it to `/data/chroma`: the `:8100` deployment, whose compose file is not versioned here, mounts that directory, and without `KNOWLEDGE_INDEX_DIR` its `index.sqlite` lands on that same volume, next to the Chroma sidecars, instead of in a directory without a volume that every deployment would empty. The `infra/` compose files set `KNOWLEDGE_INDEX_DIR=/data/index/<slug>` on a volume of its own and leave the Chroma one mounted only as the source for `migrate-index`; the image sets `KNOWLEDGE_HOME=/data/index`, the root of a deployment with `vaults.yaml`.
8. **`migrate-index` does not read Chroma vectors, and `chromadb` stops being a dependency.** What is worth keeping from the Chroma index are the sidecars (`usage_stats.json` and the learned weights of `link_graph.json`); the vectors were cut with another chunker. The subcommand prepares the index and copies those sidecars without opening the Chroma database, and the first tool call fills it. An index built with another provider, model or chunk plan is emptied and fully re-embedded when the first tool is served. The image entrypoint runs `migrate-index` without `--build` and then `serve`: embedding with `openai` takes one or two minutes and the `HEALTHCHECK` allows 20 s of startup. Without `chromadb`, the scripts that import it or package its index are removed (`scripts/export-data.sh`, `import-data.sh`, `lib/export-vault-collection.py` and `purge-code-collection.py`): the index is rebuilt from the vault and there is no snapshot to move.
9. **Local provider deferred.** A local dense model without egress was measured over `vault/cloudfrog` (50 queries, recall@5, fusion `0.7·semantic + 0.3·lexical`) and none beats `none` with FTS5 by more than one query:

   | Configuration | recall@5 | Cost of having it |
   |---|---|---|
   | `none` + FTS5 (no dense) | 0.837 | None |
   | quantized `multilingual-e5-small`, 1,000-character chunks with a 512-token guard, + FTS5 | 0.830 | 55 MB of wheels (`fastembed`, `onnxruntime`) and 135 MB of model; 3,445 chunks in 155 s |
   | `jina-embeddings-v2-base-es`, 2,500-character chunks truncated to 512 tokens, + FTS5 | 0.837 (0.853 with TF-IDF) | 55 MB of wheels and 644 MB of model; 1,487 chunks in 529 s |
   | `text-embedding-3-large` + FTS5 (the `openai` provider) | 0.930 (gate ≥ 0.890) | USD 0.1122 per full reindex |

   The extra would cost about 190 MB and between 2.5 and 9 minutes per reindex to end up where `none` already is. It does not enter this version: there is no local `ChunkPlan` or `[local]` extra. It comes back if a vault that does not accept OpenAI needs a dense model without egress, with its own measurement.
10. **The wikilink resolver fixtures live in `tests/fixtures/vaults/links/`**, outside the goldens' vault: adding files to `tests/fixtures/vault/` would move a dozen goldens for a cause unrelated to the store and would force relaxing the listings against 1.0.0 and 1.1.0.

11. **Level-2 heading chunker, 2,500 characters with 10 % overlap** (`chunker.py`, version `h2-pack-v1:2500:0.1`). It groups `## ` sections up to the target size, splits by lines the section that exceeds it, and prepends to each chunk the end of the previous one. Over `vault/cloudfrog`: 886 chunks become 1,487; the longest measures 2,750 characters instead of 11,999; chunks over 7,500 characters, which the provider silently truncated, go from 57 to 0. With the 1.1.0 TF-IDF lexicon and OpenAI, the change alone gives recall@5 0.920 (0.890 in 1.1.0). The `excerpt` of a response is taken from the chunk without its overlap. `docs/eval/sweep.md` has the sweep that fixes the size and the overlap.
12. **Wikilink resolver by path, path tail and name** (`graph.LinkIndex`, `RESOLVER_VERSION = "v2"`). It discards aliases (also `\|`), heading and block; compares in `casefold` with NFC; with several candidates the one that shares the most directories with the linking file wins and, on a tie, the smaller path; a target that is not Markdown and a link to the file itself are not an edge. Over `vault/cloudfrog`: 285 directed edges become 1,330 and connected files go from 74 to 141; `vault-lint` drops from 1,118 to 2 `E_WIKILINK_UNRESOLVED` (`docs/eval/graph.md`). `link_graph.json` stores the resolver version and an index with a different one is re-registered without embedding. Over `tests/fixtures/vault/` the edges do not change (9 and 9).
13. **`KNOWLEDGE_STRUCTURED_OUTPUT` stays at `1` by default.** ADR-042 asks for two real sessions without `structuredContent`, one from Claude Code and one from Claude Desktop via `mcp-remote`. The Claude Code one was run on 2026-10-12 with Claude Code 2.1.296 and passes; the Claude Desktop one is run by the owner on their machine and is not done, so the default does not change (result and procedure below).

### Client verification for ADR-042

Repository stdio server (`uv run cloudfrog-knowledge serve --transport stdio`), `none` provider, `VAULT_PATH=tests/fixtures/vault`, a temporary index per run (`KNOWLEDGE_INDEX_DIR`) and the configuration variables emptied so that no `.env` redirects anything. Client: `claude -p --strict-mcp-config --output-format stream-json --verbose --allowedTools mcp__knowledge-probe__search,mcp__knowledge-probe__get_document`, with the ADR-042 request (a `search` for "middleware outage" with `fields` and a `get_document` with the `file_path` and `chunk_id` of the first result).

| ADR-042 criterion | `KNOWLEDGE_STRUCTURED_OUTPUT=0` | Control with `=1` |
|---|---|---|
| What travels on the wire (`initialize`, `tools/list` and two `tools/call` over loopback HTTP with bearer) | 16 tools; `outputSchema`: 0 occurrences; `structuredContent`: 0 | `outputSchema` in `tools/list`; `structuredContent` in both responses |
| Claude Code session | Server `connected` with 16 tools; the client loads both with Tool Search, calls `search` and `get_document` without `is_error` and receives one text block per row | Same calls without `is_error`; the client hands the model the `structuredContent` (the result arrives as `{"result": [...]}`) and not the text blocks |
| Model answer | `file_path` `Runbooks/Runbook - Middleware Outage.md`, section `Runbook - Middleware Outage`, first line `# Runbook - Middleware Outage`; all three exist in that document (`rg -F`) | The same three values |

Result: Claude Code reads the text when there is no `structuredContent` and answers the same; the Claude Code criterion passes. The interactive session with `/mcp` from criterion 4 was not run: the `-p` run already exercises Tool Search (it loaded both tools with `ToolSearch`), but an interactive session remains unverified. Claude Desktop was not verified: the `knowledge-probe` entry in `claude_desktop_config.json` is a persistent change on the owner's machine and they add and remove it. Until it is done, the default stays at `1` and the "Deferred" row stays in place; when the Desktop session passes, the change to `0` is a contract version with its row under "Removed" and its goldens re-recorded.

## Deferred

| Point | Why | Goes to |
|---|---|---|
| `KNOWLEDGE_STRUCTURED_OUTPUT` at `0` by default | The Claude Code session passes (decision 13); the Claude Desktop one via `mcp-remote` is missing, which the owner runs on their machine | The first version with the Desktop session done; 2.0 at the latest |
| int8 vectors | At this scale they save 14 MB and open an unmeasured recall variable | A vault with more than about 20,000 chunks, with its measurement |
| Reciprocal rank fusion, title and section prepended to the embedded text, FTS5 `snippet()` in responses, OpenAI `dimensions=1024` | Unmeasured, or measured without gain | A measurement that wins |
| Omitting `export_hint` | Removes a key | 2.0 (ADR-042) |

## Risks

- **Section-flow coverage with no margin.** The `instructions` protocol covers 27 of 50 queries (`answer_terms` 0.540), right at the gate and one query fewer than 1.1.0 (0.560). One more query that loses its section fails the gate (`docs/eval/tokens.md`).
- **The FTS5 versus TF-IDF comparison cannot be reproduced from the repository.** Both sessions fixed the lexicon with an internal variable that the published code does not have; only FTS5 remains in the code, and its row was repeated on the published code with the same figures. The reports of the two sessions are not versioned: repeating the comparison requires writing the switch again (`docs/eval/baseline.md`).
- **The `python` fallback may choose other chunks on an exact tie.** With continuous vectors (`openai`) both paths give the same order; with vectors that have ties (the suite's bag of words) the cut at `k` may differ, which is why the goldens are recorded only with `sqlite-vec`.

## Consequences

- `search`, `search_deep` and `context_pack` change `score` and, with ties, order on the fixture; each golden that changes against `tests/golden/v1.1.0/` has its row in CHANGELOG 1.2.0. The rest of the goldens are byte-for-byte identical.
- Rows that arrive only through the lexical side carry `title`, `excerpt` and, where applicable, `needs_review` and `age_days`; memories are excluded by `type` and by folder on both sides of the search.
- `reindex` adds `index_version`; `/health` adds `index_version` and `vector_backend`.
- Each vault stores `skipped_files.json` in its own index directory.
- Processes that index the same directory take turns with `flock`, and a process's first indexing keeps the learned weights it finds in `link_graph.json`.
