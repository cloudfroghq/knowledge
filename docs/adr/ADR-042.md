# ADR-042: Contract 1.1: additive with declared changes

Status: Accepted. Amends one consequence of ADR-040 (`export_hint`) and the timing of decision 1 of ADR-041 (`structuredContent`/`outputSchema`). ADR-043 amends it at one point: in 1.2.0 `export_hint` keeps its key and changes its value, because `scripts/export-data.sh`, which packages a Chroma index the server does not read, is removed together with `chromadb`.

## Context

The contract plan called for a "strictly additive" 1.1: no existing key, default or value changes and nothing is removed. Checked against the code, that statement is false for what 1.1 needs to do. **Values** change on three fronts, without removing a key or moving a default:

1. **Order.** `find_path`, `get_related` and `get_impact` followed the traversal order of a Python `set` (they depended on `PYTHONHASHSEED`), and ties in `search` and `search_deep` had no order. In 1.1 all five have a total-order key.
2. **Text serialization.** Each `text` block stops being JSON with `indent=2` and becomes compact JSON: the same JSON once parsed, fewer tokens.
3. **Catalog.** The `tools/list` descriptions come from `contract.DESCRIPTIONS` (≤250 characters; `search_code` ≤80) instead of the docstrings; no `inputSchema` node carries `title`; `search_code` carries deprecation `_meta`; `initialize` brings `instructions` with the version on the first line.

In addition, five points of the plan and of earlier ADRs clash with the additive rule: including them in 1.1 would remove a key or change the behavior of an existing parameter.

## Decision

1. **The 1.1 rule is "additive in keys, parameters and defaults, with declared value changes".** No tool response loses a key, no existing parameter changes type or default or becomes required, and no tool disappears. The rule covers tool responses; the catalog has one declared exception: `inputSchema` stops carrying `title` (on every property and at the root), so `tools/list` loses those keys, although no name, type, default or `required` changes. The value changes above and that exception go in the "Changed (non-additive)" subsection of `docs/contract/CHANGELOG.md`, one row each. The number is 1.1.0 because none of them removes a key or changes a default; anyone who requires strict semver over values should read them as 2.0 changes.
2. **Each value change has a valve or a comparator.** Compact text is reverted per deployment with `KNOWLEDGE_TEXT_INDENT=2` (bytes identical to 1.0.0). Order is compared against `tests/golden/v1.0.0/` as a set (`tests/golden_compat.py`), and everything else from 1.0.0 is still required, as parsed JSON, over the existing keys.
3. **Five points are deferred**, with their reasons:

| Point | Plan or ADR | In 1.1.0 | Goes to | Why |
|---|---|---|---|---|
| `export_hint` of `reindex` when the vault does not declare `repo` | ADR-040 "Consequences": omit it in 1.1 | Kept identical; `vault_sync: skipped_no_repo` already says there was no pull | 2.0, with the removal of `scripts/export-data.sh` | Omitting it removes a key: the fixture does not declare `repo`, so `reindex` would lose it relative to 1.0.0 |
| `sync_confluence(dry_run=False)` → `E_WRITE_FENCED` | Plan: declared removal of 1.1 | `dry_run=False` keeps writing under `scope_prefix`, only in the default vault: with another `vault` it is `E_ARGUMENT_CONFLICT` | 2.0 | It changes the behavior of an existing parameter. The fence does not cover this path: `scripts/sync.sh` automates it, and two AcmeDrive `launchd` agents that point to nonexistent checkouts would write to the vault again without a PR if someone restored that checkout (`CLAUDE.md`, "Conventions" and "Deployments") |
| `weight` of `get_related` to 3 decimals | Plan, 1.1 section | Not rounded; `fields` allows leaving `weight` out | 2.0 | Rounding changes an existing value |
| `structuredContent`/`outputSchema` off by default | ADR-041 decision 1: they may go in 1.1 after verifying clients | Flag `KNOWLEDGE_STRUCTURED_OUTPUT`, default `1` (the 1.0.0 behavior); with `0` the two keys disappear and the catalog order does not change | 1.2, as a declared removal, if the client verification below passes; otherwise 2.0 | Switching the default to `0` removes two keys for every client that asked for nothing |
| Size of `instructions` | Plan: up to 2,048 characters | ≤600 (today 406, ~105 tokens) | — | 2,048 characters cost ~500 tokens per session, and clients truncate the field (Claude Code cuts it): the version goes on the first line and the protocol is at most five lines |

## Client verification (condition for 1.2)

The default of `KNOWLEDGE_STRUCTURED_OUTPUT` becomes `0` in 1.2 only if a real Claude Code session and a real Claude Desktop session via `mcp-remote`, against the local HTTP server, answer a `search` and a `get_document` without `structuredContent`. The result (commands, trimmed outputs, date) is recorded in this section and in the "Removed" row of CHANGELOG 1.2.0. None of this touches `~/.claude.json`, a deployment or the vault: the server only reads `vault/cloudfrog`, listens on loopback, and its index lives in the scratch directory.

### HTTP server on loopback

```bash
SCR=<scratchpad>/kp; mkdir -p "$SCR"
export KP_TOKEN="$(openssl rand -hex 24)"   # never printed nor written to the repo
MCP_TRANSPORT=http MCP_HTTP_HOST=127.0.0.1 MCP_HTTP_PORT=8765 MCP_API_KEY="$KP_TOKEN" \
KNOWLEDGE_STRUCTURED_OUTPUT=0 KNOWLEDGE_EMBEDDINGS_PROVIDER=none \
VAULT_PATH="$PWD/vault/cloudfrog" KNOWLEDGE_INDEX_DIR="$SCR/index" \
KNOWLEDGE_CONFIG_JSON= KNOWLEDGE_VAULTS= KNOWLEDGE_HOME= VAULT_REMOTE= MEMORY_HTTP_TOKEN= KNOWLEDGE_MEMORY_URL= CHROMA_PERSIST_DIR= \
uv run cloudfrog-knowledge serve --transport http
```

The empty variables are not decoration: `load_settings` loads `.env` without overriding what is already defined, so emptying them keeps a local `.env` from redirecting the index, the vault or the memory server, or from enabling a `git pull`. The HTTP variables are `MCP_HTTP_HOST`/`MCP_HTTP_PORT`; without them the server listens on `0.0.0.0:8000`.

### Claude Code

`$SCR/probe.json`, with the bearer taken from the environment (Claude Code expands `${KP_TOKEN}`; the value is not written to the file):

```json
{"mcpServers": {"knowledge-probe": {"type": "http", "url": "http://127.0.0.1:8765/mcp",
  "headers": {"Authorization": "Bearer ${KP_TOKEN}"}}}}
```

```bash
claude -p --mcp-config "$SCR/probe.json" --strict-mcp-config \
  --output-format stream-json --verbose \
  --allowedTools mcp__knowledge-probe__search,mcp__knowledge-probe__get_document \
  'Usa mcp__knowledge-probe__search con query "tenant_resolution_failed", limit 3 y fields ["file_path","chunk_id","section","score"]; luego mcp__knowledge-probe__get_document con file_path y chunk_id del primer resultado. Responde solo: file_path, section y la primera línea del contenido.' \
  > "$SCR/session-off.jsonl"
```

Criteria, all of them:

1. What travels on the wire: the same `initialize`, `tools/list` and `tools/call` via `curl` against `http://127.0.0.1:8765/mcp` (headers `Authorization: Bearer $KP_TOKEN`, `Accept: application/json, text/event-stream` and the `Mcp-Session-Id` that `initialize` returns), saved in `$SCR/wire-off.txt`: `rg -c outputSchema` and `rg -c structuredContent` give 0.
2. `session-off.jsonl`: two `tool_use` entries without `is_error` and a final answer whose `file_path`, `section` and first line exist in that document (`rg -F` over the `.md`).
3. Control: the same run with the server at `KNOWLEDGE_STRUCTURED_OUTPUT=1` answers the same `file_path` and the same `section`.
4. Interactive session: `claude --mcp-config "$SCR/probe.json" --strict-mcp-config`; `/mcp` shows `knowledge-probe` with 16 tools and the same request works with Tool Search active, which `-p` may not exercise the same way.
5. Additional control over stdio (no bearer): `probe-stdio.json` with `"command": "uv", "args": ["run", "--directory", "<checkout>", "cloudfrog-knowledge"]` and the same `env`.

### Claude Desktop (via `mcp-remote`, the AcmeDrive path)

1. The same HTTP server on loopback.
2. The owner adds a `knowledge-probe` entry to `claude_desktop_config.json`: `npx mcp-remote http://127.0.0.1:8765/mcp --allow-http --header "Authorization:Bearer ${KP_TOKEN}"` with `env.KP_TOKEN`. This is a persistent configuration change on their machine: they make it, not an agent. Restart Desktop.
3. The same two-call request in a new chat.
4. Evidence: `~/Library/Logs/Claude/mcp-server-knowledge-probe.log` shows the frames with `content` and without `structuredContent`, and the chat answer is correct; control with `=1`.
5. The Desktop entry is removed and the server is stopped.

If either of the two fails, the default stays at `1` until 2.0 and this section says what broke.

### Result

- **Claude Code**: verified on 2026-10-12 (Claude Code 2.1.296) against the contract 1.2.0 server over stdio, with the `none` provider and the test fixture, and against the same server over loopback HTTP for what travels on the wire. With `KNOWLEDGE_STRUCTURED_OUTPUT=0` there is no `outputSchema` or `structuredContent` on the wire and the session answers a correct `file_path`, `section` and first line; with `=1` it answers the same and the client hands the model the `structuredContent`. The detail is in `docs/adr/ADR-043.md` (decision 13).
- **Claude Desktop**: not verified; the `knowledge-probe` entry is added and removed by the owner. Until then, the default stays at `1`.

## Consequences

- `docs/contract/CHANGELOG.md` 1.1.0 is closed with the subsections Added, New tools, Changed (non-additive), Deprecated and Deferred; `tests/test_contract_version.py` requires that every new parameter, every new golden and every golden whose bytes differ from 1.0.0 be named there.
- `tests/golden/v1.1.0/` is recorded byte for byte with the defaults (compact text, structured output). Two repetitions of the session prove the valves: with `KNOWLEDGE_TEXT_INDENT=2` the session equals the re-indented goldens, and with `KNOWLEDGE_STRUCTURED_OUTPUT=0` it equals the goldens without `structuredContent` or `outputSchema`, with the catalog in the same order.
- The `initialize` golden stores only `serverInfo.name` and `instructions`: `serverInfo.version`, `protocolVersion` and `capabilities` belong to the `mcp` SDK and are checked against the installed package, not against a literal.
- The token goal for the `search → get_document` flow (mean ≤ 853, half the local baseline, with coverage ≥ 0.540 and recall@5 not dropping below 0.880) is met by the official measurement in `docs/eval/tokens.md` (`text-embedding-3-large` over `vault/cloudfrog`, three sessions over copies of one index of 151 files and 886 chunks). The `instructions` protocol (`fields`, `chunk_id`, `max_chars=2000`) costs 800 tokens on average (median 888, p95 1,043; −53 % versus 1,707) and covers 28 of 50 queries (0.560); recall@5 is 0.890 against 0.880, precision@5 0.304, MRR@5 0.849 and hit@5 0.980. The default read (`max_chars=4000`, no `fields`) costs 1,595 tokens on average with coverage 0.540, the baseline's. The recall difference is one query (`cf-049`) and comes from the order the branch's indexer produces, not from the contract. On the fixture the selector picks the same sections, so `search__pointers`, `get_document__chunk` and `context_pack` do not change; only `initialize` is re-recorded because of the `max_chars` in `instructions`.
