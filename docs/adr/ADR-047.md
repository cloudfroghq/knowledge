# ADR-047: Contexts live in each vault, `init` links them on the client, and the indexer skips dot directories

Status: Accepted. Complements ADR-036 (context packages exposed to each checkout with three relative links) and ADR-044 (vault write fence). ADR-048 replaces the `copy` mode for a checkout with worktrees: a real `.claude` receives the package entry by entry, and whatever the checkout versions in git is its own. This is not a contract change: the contract stays at 2.0.0, no tool changes shape and no golden moves.

## Context

The server has to be tenant-transparent: the vaults it serves are decided by `vaults.yaml` (or `VAULT_PATH`), and nothing from a project should live in the server code. Three things prevented that:

1. **The context packages lived in this repository.** `ops/contexts/<package>/` (`CLAUDE.md`, `.mcp.json`, `.claude/`) for each consuming application, the checkout registry in `config.json` → `repos` and `graph.targets`, the machine paths in `repos.local.json` (gitignored) or in `CD_*` variables, and the installation in `make ai-context` → `scripts/link-ai-context.sh`. Each tenant's content traveled with the server code.
2. **A remote server does not see the client's disk.** The HTTP deployment cannot know where a person's checkouts are nor create links in them: installing a package is, by necessity, a local task.
3. **The indexer and `vault-lint` read different sets.** `DirectoryVaultSource.markdown_files` walked `rglob("*.md")` and entered dot directories; `vault-lint` skips them. With the packages inside the vault, the agents, commands and skills of `Contexts/<app>/.claude/` would enter the index as if they were notes.

## Decision

1. **Contexts live in the vault.** `<vault>/Contexts/config.json` declares `repos` (`roots`, `groups`, `entries`) and `graph.targets` with the same shape as this repository's `config.json`, so moving it is a copy; `<vault>/Contexts/<context>/` holds each package. The schema admits two new things, compatible with what exists: a root's `env` becomes optional (it remains as a deprecated alias) and a root may declare `default`, absolute or with `~/`, which counts only if that directory exists on the machine: a suggestion nobody followed is not a declared location, and the root remains *unconfigured*, not *missing*. A `context` names a directory, never a path (`../x` is rejected), and so are two identifiers that a single variable would set.
2. **Where the checkouts are is known by the machine**, in `<config home>/knowledge/<slug>/repos.local.json`: `$XDG_CONFIG_HOME/knowledge` or `~/.config/knowledge`, the same directory as the user's `vaults.yaml`. It stores `slug`, `vault` (the vault's directory), `roots` and `repos` (the checkouts that are not at `<root>/<declared path>`). The resolution order is: `KNOWLEDGE_REPO_<ID>` and `KNOWLEDGE_<ROOT>_ROOT`; the deprecated aliases `CD_REPO_<ID>`, `CD_<ROOT>_ROOT` and the declared `env`, which keep working and are reported in `warnings`; `repos.local.json`; and the root's `default` if its directory exists. A pinned checkout wins over any root.
3. **`knowledge.repos` stays on the standard library.** It runs as `python3 -m knowledge.repos` without the virtual environment, and for that reason it never reads `vaults.yaml`, which would need PyYAML. Instead, `init` records the vault's directory and its slug inside each `repos.local.json`: the machine's files suffice to know which vaults were initialized and where their `Contexts/config.json` is. Requiring `--vault-dir` on every call was discarded (every script would have to know where each vault lives), as was reading `vaults.yaml` with a custom parser (a second implementation of the schema that drifts from the first). `--vault SLUG` and `--vault-dir DIR` exist for choosing; with neither, the single initialized vault is read, with several one has to be named, and with none this repository's `config.json` is read while it exists.
4. **`cloudfrog-knowledge init` belongs to the client.** For each registered vault that declares `Contexts/config.json`: it locates each root (a `--root [SLUG:]NAME=DIR` flag; what the machine already declares in the environment or in `repos.local.json`; the root's `default`; a walk of `--search-dir`, by default `~/Projects` and the parents of known paths, looking for git checkouts whose `origin` names a declared remote; or a prompt in the terminal, except with `--yes`), writes `repos.local.json`, pins the checkouts it found outside their declared path (only if exactly one has that remote) and installs the package in each present checkout: relative links in `link` mode, a copy in `copy` mode, plus the ignore entries in `.git/info/exclude` (or `.gitignore` with `--exclude gitignore`). It skips the checkouts that are not there. It ports the rules of `scripts/link-ai-context.sh`: in `link` mode it replaces only links; a real file or directory needs `--force`, which sets it aside as `<name>.pre-ai-context.bak-<epoch>`; a copy that drifted from the package needs `--refresh`; `settings.local.json` and `worktrees/` of a copied `.claude` are never touched. It rejects a checkout whose `origin` is another repository. It is idempotent, `--dry-run` writes nothing, `--json` prints the report, and the text ends by saying where each file lives (`vaults.yaml`, each `repos.local.json`, each linked checkout) so the person can edit it. Exit 0 if everything was handled, 1 if a vault could not be read or a package clashes with what the checkout already has, 2 if nothing could be attempted (`E_ROOT_UNKNOWN`, configuration).
5. **`init` never writes inside a vault** (ADR-044). The `repos.local.json` lives in the user's configuration directory and the links in the checkouts; a write that would land inside a served vault (a checkout inside the vault, an `XDG_CONFIG_HOME` inside the vault) is rejected with `E_WRITE_FENCED` before writing. A link is judged by where it is, not by where it points: a checkout's `CLAUDE.md` points at the vault and does not write into it. `tests/test_write_fence.py` runs `init` over a copy of the vault and requires the tree to stay intact.
6. **`doctor` warns about a pending `init`, without failing.** A served vault with `Contexts/config.json` and without `repos.local.json` on this machine appears in `init.pending`; over stdio, additionally, with the `W_CONTEXTS_INIT_PENDING` warning, and `doctor --brief` prints `knowledge doctor: init pending for vault(s) <slugs>; run: cloudfrog-knowledge init`. The exit code stays at 0: the vault is served the same with or without the packages linked, and a 1 would make the plugin hook treat it as a broken installation and not launch `jira sync --auto`. The hook now forwards any brief line that is not the `ok` one, so the warning reaches the session and a healthy doctor stays silent. Over HTTP `init` is not suggested: a deployment has no checkouts.
7. **The indexer skips dot directories**, with the same rule as `vault-lint` (`vault_source.is_hidden`): `Contexts/<app>/CLAUDE.md` is a note and can be searched; nothing under `Contexts/<app>/.claude/`, `.obsidian/` or `.trash/` is. The `/health` freshness probe walks the same set, so editing an agent does not mark the index as stale. This is a behavior change on real vaults, not a contract change: no response shape changes, and the next reindex removes from the index whatever was under a dot directory. In the local clones of the four vaults there is no `.md` in that situation; the Cloud frog deployment's clone was not checked.

## Consequences

- The golden fixture (`tests/fixtures/vault/`) has no dot entry, and `test_the_golden_vault_has_no_dot_prefixed_entry` keeps it that way: no golden changes and `tests/test_contract_frozen.py` stays green.
- The `tests/fixtures/vaults/contexts/` fixture is born (two roots, three applications, one package per application with `CLAUDE.md`, `.mcp.json` and `.claude/agents/x.md`), used by the tests of the registry, `init`, `doctor` and the indexer; all of them work with copies in `tmp_path` and their own `HOME` and `XDG_CONFIG_HOME`.
- `knowledge.contexts` is a new module of the ext group (it imports only `errors` and `repos`), next to the others in the `layers` contract; the package grows to 35 modules.
- `graph_targets` reads the registry and the `graph.targets` from the default vault's `Contexts/config.json` when it has one, and this repository's `config.json` when it does not.
- In `link` mode, a checkout's `.claude` is a link to the vault's `Contexts/<app>/.claude/`, and Claude Code writes its `settings.local.json`, its `agent-memory/` and its `worktrees/` there. The vault has to ignore them (`Contexts/*/.claude/settings.local.json`, `Contexts/*/.claude/agent-memory/` and `Contexts/*/.claude/worktrees/` in its `.gitignore`): `init` checks it with `git check-ignore` when the vault is the root of a git repository, warns with `W_CONTEXTS_GITIGNORE` without blocking, and does not check a folder without git or a vault inside another's repository. In `copy` mode, `settings.local.json`, `agent-memory/` and `worktrees/` are personal: they do not count as drift, are not copied from the package, and `--refresh` does not delete them. A checkout that keeps git worktrees inside its tree goes in `copy` mode, as ADR-036 already said.
- `vault-lint` checks `Contexts/*/CLAUDE.md` like any note, and a `CLAUDE.md` without frontmatter is an error under the 1.3 rules, unless the vault excludes them with `index.exclude` (for example `["Contexts/**"]`). Under the 1.3 rules, a file matching that pattern skips repeated stems, source links and the frontmatter rules (`E_FRONTMATTER_*`, `E_SCOPE_FOREIGN` and `W_TYPE_UNKNOWN`); the runbook and path rules still apply. The `1.2` rules, which `reindex.validation` counts, do not read the manifest and do not change. `index.exclude` is read only by `vault-lint`: the indexer still indexes those files.
- In `VAULT_PATH` mode the slug that is served is not a tenant's name: it comes from `CHROMA_COLLECTION` (blank is read as absent), then from `chroma_collection` in `config.json`, then from the `slug` in the directory's `vault.yaml` (only if it is a valid slug, because it builds paths; an invalid one warns with `W_VAULT_SLUG_MISMATCH` and is not used) and, with none of those, `vault`. With the slug from `vault.yaml`, the credential variables the vault names (`PERSONAL_TYPESAFE_API_KEY` in a `personal` vault) match the served vault and `E_MANIFEST_INVALID` no longer rejects them as foreign; a `CHROMA_COLLECTION` different from the vault's `slug` still warns and does not rename the index. The index of anyone who sets none of `KNOWLEDGE_INDEX_DIR`, `CHROMA_PERSIST_DIR` or `KNOWLEDGE_HOME` lands in `<root>/.data/<slug>` with the slug from its `vault.yaml`, or in `<root>/.data/vault` if it has none and does not set `CHROMA_COLLECTION`: a deployment that relied on that directory sets one of the three variables. The Cloud frog deployment (`VAULT_PATH`, `slug: cloudfrog` in its `vault.yaml` and an explicit `KNOWLEDGE_INDEX_DIR`) resolves the same slug and the same index directory (test in `tests/test_vault_registry.py`). The slug appears in responses (`list_vaults`, `reindex`, `context_pack`) but its shape does not change: the golden launcher (`tests/golden_stdio_server.py`) sets `CHROMA_COLLECTION=cloudfrog` because the test vault does not declare a `vault.yaml`, and the goldens stay byte for byte. `infra/compose.yml` no longer forces `CHROMA_COLLECTION` in single-vault mode.
- The review queue matches the lint: what `index.exclude` covers does not count as "without `last_updated`", nor as stale, nor as an unreadable date, neither in `get_stale_docs` nor in `scripts/weekly-stale-report.py`. Both go through `review.is_curated`, which receives the predicate from `vault_lint.index_exclude_matcher` (the same globs as the lint): the server takes them from `VaultSpec.index_exclude`, which comes from the vault's `vault.yaml`, and the report reads the `vault.yaml` of the vault it reviews. A `vault.yaml` the report cannot read is noted as `unwalkable`, and `--fail-on-stale` does not certify it. The shape of the `get_stale_docs` response does not change, only which files enter, and no golden changes (the goldens' vault declares no manifest). The `needs_review` annotation on `search` rows does not go through `is_curated` and does not change.
- The `init` scan reads each checkout's `origin` from the git config file (`repos.read_origin`: a plain config, a linked worktree or a `.git` file with `gitdir:`) and lets `git config --get` answer what that reader does not model (`include`, `includeIf`, quotes, comments after the value, `extensions.worktreeConfig`). An `init` with several vaults scans only once (`contexts.memoized_scan`). With 2,016 directories and 62 repos the scan takes about 60 ms; launching `git` per repo costs about 13 ms each.
- `init` installs only in a checkout that proves to be the declared repository: a registry `path` that leaves its root with `..` is `E_CONTEXTS_INVALID` (a package's `.mcp.json` declares commands, and none may land outside the root), and a checkout whose `origin` cannot be read (no remote, no `.git`) stays `unverified`, exits with 1 and receives nothing except with `--force`. A `.claude`, `CLAUDE.md` or `.mcp.json` that is already a symlink foreign to `Contexts/<package>/` belongs to the user, like a file of their own: conflict, or set aside with `--force`.
- A vault without applications declares `repos.roots: []` and `repos.entries: []` (and `graph.targets: []`): the empty registry is valid only in a vault's declaration. `init` reports it as `no-apps`, exits 0 and does not even write `repos.local.json`, because there is nothing from this machine to register; `doctor` does not count it as `init pending`. A `roots` or `entries` that is not an array, a malformed entry or an entry hanging from an undeclared root are still `E_CONTEXTS_INVALID`, and the root `config.json` of the repository still requires roots and entries.
- `ops/contexts/`, the root `config.json`, `scripts/link-ai-context.sh` and the `Makefile` targets stay in place and keep working: while no vault is initialized, `python3 -m knowledge.repos` reads this repository's declaration. The `CD_*` variables keep working as aliases.

## Deferred

| Point | Why | Goes to |
|---|---|---|
| Move `ops/contexts/` and `config.json` → `repos`/`graph` into each vault's `Contexts/` | It is vault content: a human PR per vault with its owner as reviewer (D-11) | The data-migration block |
| Delete `ops/contexts/`, the root `config.json` `repos`, `scripts/link-ai-context.sh` and the `Makefile` targets, or make them delegate to `init` | Until the migration they are the only source of the packages | The same block |
| `make graphs` takes the targets from the default vault (`graph_targets`) and the state of each checkout from the single initialized vault (`knowledge.repos`) | They coincide while there is a single vault with `Contexts/`; with several, one must be chosen explicitly | The same block |
| Retire the `CD_*` aliases | Current scripts and canaries use them | When no consumer names them |
