# ADR-050: the package is published to PyPI, npm and as a git tag

Status: Accepted. Supersedes point 3 of the decision in [`docs/adr/ADR-040.md`](ADR-040.md) and its D-H1 row (private distribution via `git+ssh`, no PyPI). This is not a contract change: the contract stays at 2.0.0, no tool changes shape and no golden moves. What changes is how the package is installed.

## Context

`cloudfrog-knowledge` was consumed only via `git+ssh` pinned to a tag of a private repository: every machine needed an SSH key with read access, and `uvx` queried the remote on every startup. The `cloudfroghq/knowledge` repository is now public, under the PolyForm Shield 1.0.0 license. Whoever installs the CLI for `init` and `doctor`, or registers it as an MCP server, has no reason to have `uv` or to know about tags: many MCP clients are configured with `npx`.

## Decision

1. **Three channels, one version.** Each tag `v<x.y.z>` is the release: the tag itself (`uvx --from git+https://github.com/cloudfroghq/knowledge.git@v<x.y.z>`), the `cloudfrog-knowledge` project on PyPI and the `@cloudfrog/knowledge` package on npm. `scripts/check-version.sh` requires the same version in `pyproject.toml`, `plugin.json`, `.mcp.json`, `npm/package.json` and `uv.lock`, and `publish.yml` compares it with the tag before publishing.
2. **The npm package reimplements nothing.** `@cloudfrog/knowledge` has no dependencies: it downloads a pinned version of `uv` from its GitHub release, verifies it against the SHA-256 the package carries (generated from the release's `.sha256` files when preparing it, never queried at runtime), stores it in the user's cache with an atomic install, and runs `uv tool run --managed-python --python 3.12 --from cloudfrog-knowledge==<its version> <command>`. `CLOUDFROG_KNOWLEDGE_UV` points to your own `uv`.
3. **Two names for the same CLI.** `[project.scripts]` installs `cloudfrog-knowledge` and `knowledge`, both `knowledge.cli:main`; the npm package exposes the same two binaries. The usage, `--version` and the hints of `doctor` and `init` name the one that was run; `KNOWLEDGE_COMMAND_LABEL` still takes precedence over both.
4. **Publishing without secrets.** `.github/workflows/publish.yml` publishes each tag with trusted publishing (OIDC): a read-only job builds and verifies, and only the publishing job has the `release` environment and `id-token: write`. Each registry is skipped only if that exact version already exists. Only GitHub actions, pinned by SHA; `uv` comes from its release archive verified by SHA-256 (`scripts/ci-install-uv.sh`), not from the `astral.sh` installer, which verifies nothing.
5. **The first npm version is published by hand.** npm configures a trusted publisher only on a package that exists: the owner of the `@cloudfrog` scope publishes the first version from their machine and then registers `publish.yml` as publisher ([`docs/runbooks/ci-ring1.md`](../runbooks/ci-ring1.md), section 7).

## Consequences

- Installing no longer requires an SSH key or access to the repository, and a pushed tag is public within minutes and forever: PyPI and npm do not accept republishing a version, so a wrong tag is corrected with another one, never by moving it.
- `uv` ignores the `requires-python` upper bound when choosing an interpreter, so the documentation, the plugin and the npm package ask for an explicit `--python 3.12`.
- Raising the npm package's `uv` version means regenerating `npm/lib/uv-release.json` (`node npm/scripts/uv-release.js <version>`) and moving the workflows' installer to the same version: `tests/test_npm_package.py` requires them to match.
- The first npm version ships without provenance; from the next one on, `npm publish --provenance` signs it from the workflow.
