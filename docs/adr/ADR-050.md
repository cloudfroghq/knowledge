# ADR-050: el paquete se publica en PyPI, en npm y como tag de git

Estado: aceptado. Supera el punto 3 de la decisión de `docs/adr/ADR-040.md` y su fila D-H1 (distribución privada por `git+ssh`, sin PyPI). No es un cambio de contrato: el contrato sigue en 2.0.0, ninguna tool cambia de forma y ningún golden se mueve. Lo que cambia es cómo se instala el paquete.

## Contexto

`cloudfrog-knowledge` se consumía solo por `git+ssh` pineado a un tag de un repositorio privado: cada máquina necesitaba una llave SSH con acceso de lectura, y `uvx` consultaba el remoto en cada arranque. El repositorio `cloudfroghq/knowledge` ahora es público, con licencia PolyForm Shield 1.0.0. Quien instala el CLI para `init` y `doctor`, o lo registra como servidor MCP, no tiene por qué tener `uv` ni saber de tags: muchos clientes MCP se configuran con `npx`.

## Decisión

1. **Tres canales, una versión.** Cada tag `v<x.y.z>` es la release: el tag mismo (`uvx --from git+https://github.com/cloudfroghq/knowledge.git@v<x.y.z>`), el proyecto `cloudfrog-knowledge` de PyPI y el paquete `@cloudfrog/knowledge` de npm. `scripts/check-version.sh` exige la misma versión en `pyproject.toml`, `plugin.json`, `.mcp.json`, `npm/package.json` y `uv.lock`, y `publish.yml` la compara con el tag antes de publicar.
2. **El paquete de npm no reimplementa nada.** `@cloudfrog/knowledge` no tiene dependencias: descarga una versión fija de `uv` desde su release en GitHub, la verifica contra el SHA-256 que trae el paquete (generado de los `.sha256` de la release al prepararlo, nunca consultado en ejecución), la guarda en la caché del usuario con una instalación atómica y corre `uv tool run --managed-python --python 3.12 --from cloudfrog-knowledge==<su versión> <comando>`. `CLOUDFROG_KNOWLEDGE_UV` apunta a un `uv` propio.
3. **Dos nombres para el mismo CLI.** `[project.scripts]` instala `cloudfrog-knowledge` y `knowledge`, ambos `knowledge.cli:main`; el paquete de npm expone los mismos dos binarios. El uso, `--version` y las pistas de `doctor` e `init` nombran el que se corrió; `KNOWLEDGE_COMMAND_LABEL` sigue mandando sobre los dos.
4. **Publicación sin secretos.** `.github/workflows/publish.yml` publica cada tag con trusted publishing (OIDC): un job de solo lectura construye y verifica, y solo el job de publicación tiene el environment `release` e `id-token: write`. Cada registro se salta solo si esa versión exacta ya existe. Solo acciones de GitHub, fijadas por SHA; `uv` sale de su archivo de release verificado por SHA-256 (`scripts/ci-install-uv.sh`), no del instalador de `astral.sh`, que no verifica nada.
5. **La primera versión de npm se publica a mano.** npm configura un trusted publisher solo sobre un paquete que existe: el dueño del scope `@cloudfrog` publica la primera versión desde su máquina y después registra `publish.yml` como publicador (`docs/runbooks/ci-ring1.md`, sección 7).

## Consecuencias

- Instalar ya no exige llave SSH ni acceso al repositorio, y un tag empujado es público en minutos y para siempre: PyPI y npm no aceptan volver a publicar una versión, así que un tag equivocado se corrige con otro, nunca moviéndolo.
- `uv` ignora el tope de `requires-python` al elegir intérprete, así que la documentación, el plugin y el paquete de npm piden `--python 3.12` explícito.
- Subir la versión de `uv` del paquete de npm es regenerar `npm/lib/uv-release.json` (`node npm/scripts/uv-release.js <versión>`) y mover el instalador de los workflows a la misma versión: `tests/test_npm_package.py` exige que coincidan.
- La primera versión de npm sale sin procedencia; desde la siguiente, `npm publish --provenance` la firma desde el workflow.
